# agent-pilates-studio

Progetto per installare e aggiornare [Hermes Agent](https://hermes-agent.nousresearch.com/), provarlo in locale e collegarlo a PostgreSQL, OpenRouter e WhatsApp Business.

## Stato

La v0.1.0 include una configurazione locale Compose per PostgreSQL e Hermes, con OpenRouter, il gateway WhatsApp Cloud nativo e un tool SQL diretto. Una prova reale ha verificato la conversazione WhatsApp tramite Hermes e OpenRouter e l'accesso SQL con il ruolo limitato.

## Scaffold e verifiche locali

Per lo scaffold servono Node.js LTS 24.14.0 e npm 11.9.0, le versioni usate per le verifiche. Il progetto accetta Node.js dalla 24.14.0 alla 24.x e npm dalla 11.9.0 alla 11.x; `.nvmrc` indica la versione di Node.js verificata. Con `nvm` si possono usare `nvm install` e `nvm use` dalla directory del progetto.

Da una copia pulita del repository:

```bash
npm ci
npm run lint
npm run typecheck
npm test
npm run build
```

Il gate rapido comprende lint, controllo dei tipi, test unitari e build; `npm ci` prepara le dipendenze da lockfile. `npm test` ricompila e usa il runner Node.js senza isolamento a processi: i test lavorano solo in memoria, senza filesystem, processi figli, Git, rete o Docker. `npm run build` rigenera `dist/`, includendo codice e test; la compilazione stessa usa filesystem e processi.

Le prove con effetti reali sono separate: `npm run test:local` verifica Git, file, processi e contratto CI; `npm run test:pi` richiede Pi 1.5.0; `npm run test:pi-package` richiede inoltre Git, Python 3 e rete per il pacchetto Pi pubblico e le sue dipendenze di test; `npm run test:claude` verifica il plugin con Claude Code (runtime verificato e CI configurata con 2.1.323), Git e Python 3, senza un modello; `npm run test:db`, `test:hermes`, `test:author`, `test:compaction`, `test:upgrade` e `test:start` richiedono Docker Compose. Eseguirle durante il lavoro quando servono per dimostrare i criteri; alla chiusura della versione eseguire tutte le suite di integrazione. Le prove end-to-end reali richiedono anche servizi e credenziali esterni.

## Scenari conversazionali con OpenRouter

`scenarios/basic.json` descrive lo stato iniziale, i messaggi sintetici, i contenuti attesi e lo stato del database dopo ogni turno. Per eseguirlo servono Node.js/npm, Docker Compose su Linux con accesso dell'host alle reti bridge Docker, rete Internet e una chiave OpenRouter valida nell'ambiente privato `OPENROUTER_API_KEY`. Non servono credenziali Meta. Dopo `npm ci`, impostare la chiave tramite un gestore di segreti o un input privato, senza inserirla nella cronologia della shell, poi eseguire:

```bash
npm run test:conversation
# In alternativa, un solo scenario:
CONVERSATION_SCENARIO=consultazione-pianificazione npm run test:conversation
```

Il modello predefinito è `openai/gpt-6.1-terra`; l'identificativo opzionale `CONVERSATION_MODEL` ne sceglie un altro su OpenRouter. Il comando usa un progetto Compose casuale con database e volume Hermes nuovi, webhook sintetici firmati e un sostituto locale dell'API Meta in uscita; il modello è reale. Disabilita i messaggi di avanzamento e configura un canale home sintetico; non filtra l'avviso del canale home e segnala errore se riappare. Un relay sul socket Unix privato dello scenario inoltra le richieste a OpenRouter: la chiave reale resta nell'ambiente e nella memoria del processo host, non viene copiata nei file o nei container; i file temporanei contengono solo credenziali sintetiche. La rete del progetto non è una sandbox generale. Non usa il database, il gateway o i segreti operativi. Nessun messaggio, numero o segreto è stampato intenzionalmente.

Il comando riporta `OK` o `ERRORE` per scenario ed esce con codice non zero per risultati inattesi, errori o pulizia incompleta. Il catalogo copre nome e presentazione per due interlocutori sintetici, saluto e richiesta iniziale senza proposte spontanee di profilo nei primi turni, nome e cognome censiti diversi dal nome del profilo WhatsApp o in sua assenza, registrazione, gruppi, chiarimenti, attribuzione dell'autore, consultazione per giorno, fascia, orario, cliente e settimana, disattivazioni esplicite, cambiamenti impliciti, variazioni di gruppo e storico. Comprende partecipazioni previste di lezioni extra e recuperi (lezione di oggi non ancora iniziata con presenza futura rifiutata e annullamento, nome simile già censito, data ambigua, cliente già atteso per regola e «c'erano tutti» che include il cliente previsto), presenze e assenze, distinzione del tipo, chiarimenti sugli attesi non citati, assenze anticipate, conferme, conflitti, correzioni, annullamenti, consultazione dello storico e statistiche con valori attesi, inclusi clienti senza registrazione valida e presenze extra. Verifica clienti, autori, date, motivi, associazioni e stato delle regole, accettando diverse scomposizioni senza associazioni mancanti o duplicate. Confronta le righe tra turni per rilevare cancellazioni, riscritture o modifiche a disattivazioni precedenti; i divieti del database sono verificati separatamente su PostgreSQL reale. Gli indicatori delle risposte sono lessicali: per i gruppi richiesti verifica orario e clienti sulla stessa riga e nella sezione del giorno, ma non verifica il significato completo né associa ogni data al relativo evento. Le esclusioni sul profilo possono rifiutare una negazione innocua e non riconoscere proposte formulate diversamente. Gli esiti non garantiscono il comportamento futuro del modello.

Ogni scenario registra il mittente sintetico come gestore e insegnante censito, con un nome diverso dal profilo WhatsApp inviato nel webhook, e censisce gli insegnanti dello scenario tramite le sole funzioni gestionali fidate, come farebbe `/anagrafica`; l'agente non crea insegnanti. Gli scenari degli insegnanti coprono cognome mancante e nome ambiguo, fasce e orari, sovrapposizioni con e senza conferma, disattivazione parziale, «alleno io» e «l'ho tenuta io» anche con un'identità dichiarata falsa, e insegnanti sconosciuti che richiedono il censimento del gestore senza essere creati. Dopo ogni turno confrontano l'intera anagrafica, autori e storico, e la copertura degli intervalli al minuto, inclusi gli estremi e le parti residue; controllano anche che clienti e presenze non cambino. Le indicazioni coprono lezioni passate e future anche senza clienti o presenze, sostituzioni singole e multiple con elenco e conferma, rifiuti e chiarimenti senza scritture, duplicati, «l'ho tenuta io» e correzioni tramite annullamento. Il confronto verifica tutte le indicazioni, incluse le annullate, con insegnante e ID coerenti, data, ora al minuto, autore, istanti e motivo, preservando regole e registrazioni estranee. Le consultazioni per insegnante coprono chi ha tenuto o terrà una lezione, con indicazione, insegnante atteso o sostituzione annullata, lezioni, conteggi e presenti di un insegnante in un mese, lezioni senza insegnante della settimana scorsa, regole attive e insegnante atteso per giorno, fascia e orario, periodi senza risultati e storico di regole e indicazioni; ogni turno verifica lo snapshot completo invariato e, per i conteggi, l'uso di aggregazioni SQL. Gli autori attesi sono il numero del mittente e il nome censito, mai il profilo WhatsApp; le regole senza data storica sono create al momento della prova e valgono solo per le lezioni successive. Regole e indicazioni con date storiche, eventualmente disattivate o annullate con motivo fisso, sono inserite dal migratore nelle righe private disabilitando soltanto i trigger autore di regole e indicazioni nella transazione di preparazione e riattivandoli prima del commit; dopo il commit si verificano trigger attivi, orari locali validi, date, autori e motivi. I controlli del database vengono valutati anche quando fallisce il controllo lessicale della risposta; la diagnostica contiene solo indicatori ed entità contate, non testi, query o risultati grezzi.

Ogni scenario usa uno stack nuovo e parte da stato vuoto. Alcuni scenari preparano nel database isolato clienti e regole sintetici, anche disattivati in date diverse, con autore e date fissati; usano il contesto autore riservato al ruolo di migrazione, mai disponibile all'agente. Negli scenari delle presenze e assenze il confronto comprende tutte le registrazioni, anche annullate, con cliente, data, ora, esito e autore; per gli annullamenti controlla data, autore e motivo non vuoto, oltre alle regole invariate e ai clienti creati. Le date relative `$TODAY`, `$YESTERDAY`, `$NEXT_MONDAY`, `$LAST_MONDAY` e `$LAST_SATURDAY` (il lunedì e il sabato più recenti prima di oggi) e `$LAST_WEEK_MONDAY` (il lunedì della settimana precedente), eventualmente con offset in giorni, sono calcolate in Europe/Rome all'inizio dello scenario, anche negli istanti delle fixture. `$LATER_TIME` è un orario di oggi due ore dopo l'ora corrente; gli scenari che lo usano falliscono senza turni se cadrebbe dopo la mezzanotte, quindi vanno eseguiti prima delle 22:00. Negli scenari delle partecipazioni previste il confronto comprende anche quelle annullate, con autore, istanti e motivo. Le fixture sintetiche inseriscono anche presenze e assenze storiche, eventualmente annullate, disabilitando il trigger autore solo nella transazione di preparazione del migratore e riattivandolo prima dei turni; date, autori, motivi e vincoli temporali delle fixture sono verificati. Per le consultazioni si confronta l'intero snapshot prima e dopo ogni turno. Nei turni statistici indicati il launcher di prova conta le query SELECT riuscite contenenti una funzione aggregata, comunicando al sostituto Meta solo un marcatore fisso, senza query, parametri o risultati. Il controllo è lessicale e non prova che il risultato sia stato usato. I conteggi nella risposta sono verificati con indicatori lessicali vicini alle etichette, non con un'analisi semantica completa. Un attraversamento della mezzanotte durante lo scenario può causare un errore della prova, da riesaminare. `CONVERSATION_SCENARIO` seleziona facoltativamente un ID del catalogo; lo strumento è escluso da CI e `npm test`.

Per una diagnosi mirata già autorizzata, `CONVERSATION_DIAGNOSTICS=1 CONVERSATION_SCENARIO=consultazione-presenze-statistiche npm run test:conversation` aggiunge categorie di operazioni e indicatori di risposta, non query, parametri o testi grezzi. L'opzione è spenta per default ed è ammessa solo per i tre casi `consultazione-presenze-statistiche`, `assenza-anticipata-singola-annullamento` e `consultazione-pianificazione`. Gli indicatori lessicali non sono una valutazione semantica completa; l'opzione non autorizza nuove chiamate esterne né tentativi ripetuti fino al verde.

Le chiamate OpenRouter sono a pagamento e possono richiedere più richieste per turno. Al 2026-11-06 il catalogo OpenRouter indicava per il modello predefinito circa **1 USD/milione di token in ingresso e 5 USD/milione in uscita**: ad esempio 10.000 token in ingresso e 2.000 in uscita costerebbero circa 0,02 USD. Sono valori indicativi, non un preventivo; verificare prezzi e limiti correnti prima della prova. Registrare data, modello, commit, esito e limiti senza trascrivere messaggi, numeri o segreti; vedere `docs/operations/TEC-012-prove.md`.

Il comando tenta di rimuovere container, reti, volumi, immagine temporanea e segreti anche in caso di errore o interruzione gestita. Un arresto forzato, un guasto Docker o del sistema possono impedirlo: verificare e rimuovere solo le risorse del progetto casuale `pilates-conv-*` e le directory temporanee `pilates-conversation-*`, senza toccare gli stack operativi. Non avviare streaming remoto dei log del tunnel; questa prova non usa il proxy pubblico né dimostra l'accettazione privacy o il funzionamento di Meta reale.

## Identità e gestione guidata dell'anagrafica

Chi scrive è riconosciuto solo dal numero WhatsApp autenticato, cercato nell'unica anagrafica degli insegnanti nel database ([ADR-003](docs/adr/ADR-003-unified-teacher-identity.md)). Possono usare l'agente soltanto gli insegnanti censiti con telefono e accesso abilitato: per loro il nome nella conversazione, il riconoscimento di «io» e l'autore delle nuove operazioni sono nome e cognome censiti, mai il nome del profilo WhatsApp. Un numero non censito, incompleto o revocato riceve solo il testo fisso «Accesso non abilitato. Per usare l'assistente dello studio rivolgiti al gestore.», senza turno del modello, sessione o accesso ai dati. L'unico numero personale in configurazione è quello del gestore (`PILATES_MANAGER_PHONE`), da cui deriva il canale home; allowlist, collegamenti numero–insegnante e canale home separato non esistono più.

Il gestore mantiene l'anagrafica dalla propria chat con `/anagrafica`: `elenco`, `nuovo`, `completa ID`, `correggi ID`, `numero ID`, `revoca ID` e `abilita ID`. Il sistema raccoglie i dati in passaggi separati e richiede `/conferma <codice>` sul riepilogo, entro dieci minuti; `/annulla` esce senza salvare. Il gestore non ancora censito riceve obbligatoriamente il censimento iniziale con il proprio numero autenticato, prima di poter lavorare sui dati dello studio; le persone preesistenti non vengono duplicate. Non può revocare sé stesso o cambiare il proprio numero. Censimenti, correzioni, revoche, riabilitazioni e cambi di numero hanno effetto senza riavvio. Un cambio di numero conserva l'identità e i dati ma apre una chat vuota; un numero assegnato a un'altra persona non eredita la conversazione precedente.

Citare un insegnante non censito in una regola o indicazione non lo crea: Ambrogio risponde che serve il censimento del gestore. Gli insegnanti già presenti prima dell'anagrafica unica restano nelle lezioni senza telefono finché il gestore non li completa, ma non accedono all'agente. Messaggi e risposte gestionali non passano da Hermes, dalla sua cronologia o dal modello; telefoni dell'anagrafica e degli autori non sono leggibili con SQL dal ruolo del modello. [Percorso, confini e limiti della gestione](docs/operations/US-017-gestione.md) · [prove dell'attivazione](docs/operations/TEC-042-prove.md).

L'aggiornamento da un'installazione precedente non importa allowlist, collegamenti numero–insegnante o nomi del profilo WhatsApp, anche se i vecchi file sono ancora presenti: quei file bloccano l'avvio finché non vengono rimossi. Su un database nuovo il gestore completa il censimento iniziale in chat e poi censisce gli altri; i nuovi censimenti richiedono nome, cognome e telefono. Censire una persona non la preregistra sul numero di test Meta. Il trasferimento della funzione di gestore a un'altra persona già censita e il cambio del numero della stessa persona sono procedure dell'operatore, distinte e non disponibili in chat: allineano configurazione e anagrafica, tolgono i privilegi gestionali al numero precedente e hanno un recupero. Il cambio della stessa persona conserva l'ID e blocca l'accesso dal numero sostituito; la chat del nuovo numero è vuota. Backup e cronologie precedenti restano dati privati, non diventano anonimi. [Procedura](docs/operations/TEC-035-produzione.md) · [prove della transizione](docs/operations/TEC-043-prove.md).

## Consultazione del backlog

Serve Python 3.10 o successivo, con la sola libreria standard. Dalla radice del progetto:

```bash
python3 .agents/tools/backlog.py status
python3 .agents/tools/backlog.py status --branches
python3 .agents/tools/backlog.py show TEC-044 --branches --no-fetch
python3 .agents/tools/backlog.py docs
python3 .agents/tools/backlog.py export --json --branches --no-fetch
```

`python3 .agents/tools/backlog.py docs --for <ID>` elenca i file necessari per un item, incluse sezioni del processo, ADR e voce del modulo; `--json` espone anche i riferimenti non risolti. `backlog check` valida file e sezioni dei riferimenti `PROCESS §N` e `process/<nome> §N`.

Senza `--branches` si consulta solo il checkout corrente. `status`, `list`, `ready`, `show` ed `export` accettano `--branches` e `--no-fetch`: gli stati sono risolti dai branch item locali e remote-tracking non integrati in `main` locale o nel branch predefinito di un remote. Il locale prevale sull'omonimo remoto; sul branch dell'item prevale la sua copia di lavoro; fra branch concorrenti prevale il commit più recente. Un item presente solo in un branch non viene aggiunto alla vista. `show` testuale indica provenienza e altri branch; `export --json` li espone in `branches.items`, insieme all'esito del fetch e ai remoti. `show --json` restituisce invece il solo record, senza metadati di provenienza, come nel template.

Il fetch non richiede input e ha timeout di 10 secondi: usa `origin` se configurato, altrimenti il remote scelto da Git. `--no-fetch` usa i riferimenti già disponibili. Un errore è un avviso, non impedisce la consultazione dei dati noti. Le viste non scrivono i file del working tree; il fetch può aggiornare o eliminare riferimenti remote-tracking e contatta il remote configurato. I dati possono essere obsoleti e non costituiscono un lock o una garanzia di assenza di lavoro concorrente. Pi e Claude Code delegano la risoluzione a questa stessa CLI.

Requisiti e design sono cartelle di file piccoli: `docs/requirements/` (README con obiettivo, attori e scope, glossario, accettazione e un file per ogni `REQ-…`) e `docs/design/` (README con decisioni iniziali e aperte e un file per argomento). `backlog docs` li elenca e `backlog check` verifica che i riferimenti degli item esistano; i file descrivono lo stato attuale, mentre lo storico resta nel backlog, negli ADR e in git.

## Configurazione Claude Code

Il pannello richiede **Claude Code 2.1.287 o successivo**, Python 3.10+ e Git per gli stati dei branch; è stato esercitato con Claude Code **2.1.323**. Avviare `claude` dalla radice del progetto e, dopo aver revisionato le risorse, accordare fiducia al progetto. Il collegamento versionato `.claude/skills` espone il plugin `.agents/skills/backlog-overlay/`: il manifest e `hooks/hooks.json` lo caricano senza modificare impostazioni personali. Non ha `SKILL.md`, non è una nuova skill e non viene proposto come istruzione al modello. Dopo aver accordato fiducia in una sessione già aperta, usare `/reload-plugins` per caricarlo. Il plugin esegue codice con i permessi dell'operatore: la fiducia non è una sandbox.

`/backlog` apre un pannello di sola lettura accanto alla conversazione, anche durante un turno, e ne richiede il focus. Se compare l'avviso, **ctrl+x Tab** assegna la tastiera al pannello. I tasti sono:

- `n` / `b`: item successivo / precedente; `g` / `e`: primo / ultimo;
- `t`, `p`, `s`: filtri per tipo, priorità e stato; `x`: ripristina i filtri iniziali;
- frecce: scorrimento del contenuto, gestito dall'interfaccia Claude Code;
- `r`: rilegge backlog e branch; Esc o `q`: chiude.

I filtri iniziali sono `Type: all · Priority: all · Status: Todo` e restano nella sessione. La vista mostra prima il checkout, poi gli stati locali e infine quelli dopo il fetch, con provenienza, branch concorrenti e avviso di fetch fallito. Il plugin non modifica gli item; il fetch ha gli effetti e i limiti descritti sopra. Le esportazioni asincrone hanno timeout di 30 secondi: un errore di fetch conserva i dati noti. Per ricaricare il codice usare `/reload-plugins` o riavviare Claude Code. I tipi eventualmente generati in `.claude-plugin/types/` del plugin sono esclusi da Git; `types/index.d.ts` è invece il contratto condiviso versionato.

`npm run test:claude` esegue in isolamento il validatore e tre prove native del modulo con effetti host sostituiti, alimentate da export reali della CLI su fixture sintetiche; una TUI reale verifica fiducia, caricamento tramite il collegamento, tasti, scorrimento, filtri, riapertura, aggiornamento, errori e branch. Usa directory personali temporanee, una chiave sintetica e un endpoint loopback senza modello, verificando l'assenza di richieste di inferenza. Non legge configurazioni personali, non prova tutte le versioni o tutti i terminali e non è una sandbox di rete. Il manifest upstream non dichiara autore: il validatore normale passa con avviso, non quello `--strict`; non è rivendicata l'idoneità alla pubblicazione nel catalogo plugin. [Evidenze e limiti](docs/TEMPLATE-ORIGIN.md#verifica-di-tec-044).

## Configurazione Pi

Con Node.js 24 e Pi installati, avviarlo dalla radice del progetto, senza build:

```bash
node scripts/start-pi.mjs
# Per scegliere una sessione:
node scripts/start-pi.mjs --resume
```

Il launcher sincronizza `.pi/workflow.json` nel normale `.pi/settings.json` locale e ignorato **prima** di avviare Pi, inoltrando argomenti ed esito. Le sole chiavi gestite sono `packages`, `skills`, `extensions` e `prompts`: aggiunte, sostituzioni e rimozioni non lasciano residui. Sono ammesse liste di stringhe (anche filtri `!`, `+`, `-`); i pacchetti possono essere stringhe o oggetti con `source`, `autoload` booleano e filtri skills/extensions/prompts. Altre chiavi, inclusi `themes` e `theme`, non sono ammesse nel manifest. Le directory convenzionali restano soggette alla scoperta di Pi.

Provider, modello, thinking generale e per modello, compattazione, temi disponibili e selezionati, UI, stato interno e valori futuri/annidati restano locali. Il launcher non li azzera e non riscrive un settings già allineato. Modificare il manifest per condividere risorse: modifiche dirette alle chiavi gestite nel settings (anche tramite `pi config --local` o `pi install --local`) vengono riallineate al prossimo avvio previsto. L'avvio diretto `pi` **non garantisce la sincronizzazione**; `/reload` non esegue il generatore.

Il launcher non accorda fiducia autonomamente. Manifest/settings malformati o non oggetti e percorsi non sicuri fermano l'avvio senza stampare contenuti personali. Sono rifiutati `.pi` simbolica/non directory/scrivibile da altri e settings simbolici, directory, FIFO o con hard link. La sostituzione usa un file privato `0600` e rename atomico nella stessa directory. Usare un solo operatore senza Pi concorrenti durante la preparazione: il gruppo Unix deve essere fidato; non è un lock contro scrittori concorrenti, ACL o host compromessi.

Il repository versiona `.pi/workflow.json`, il template `.pi/prompts/work-alone.md`, l'estensione `.pi/extensions/backlog/index.ts` e le skill in `.agents/skills/`. Dopo aver verificato le risorse, accordare fiducia al progetto in Pi per caricare le impostazioni e le risorse locali: la fiducia non è una sandbox e le estensioni possono eseguire codice. Il manifest contiene solo riferimenti ai pacchetti e selezione delle risorse; le preferenze restano nel settings locale. La disponibilità di pacchetti o percorsi su un altro computer non è garantita. Rivedere le modifiche al file versionato prima di condividerle e non inserirvi credenziali.

I tool `question` e `questionnaire` provengono dal pacchetto pubblico `agent-harness-stuff`, fissato in `.pi/workflow.json` al commit `44f36742d47a4e83504abb9bdc0427be5f09ed82` sul branch `task/TEC-018-stato-attesa-tool-pi`. Sono un adattamento MIT di `pi-question-tool` 0.1.1 di SakikoTogawa233, con licenza e attribuzione conservate nel pacchetto. Il pacchetto originale `npm:pi-question-tool` non deve essere caricato contemporaneamente. Quando attendono una risposta, Pi 1.5.0 segnala `blocked`/`question` via OSC 7501 con un titolo fisso privo del testo della domanda; il terminale deve supportare il protocollo. Alla risposta o all'annullamento Pi ripristina lo stato precedente. I dati mostrati nelle normali interfacce e sessioni Pi restano sensibili.

Per aggiornare questi tool, revisionare il nuovo codice, assicurarsi che il commit sia pubblicamente raggiungibile e sostituire il riferimento fissato in `.pi/workflow.json` e riavviare tramite il launcher; `pi update --extensions` non sposta un commit fissato. Ricaricare con `/reload` o riavviare Pi. Il branch remoto che contiene il commit deve restare disponibile finché il riferimento è in uso; la fiducia nel progetto resta necessaria.

In una sessione Pi con fiducia accordata, `/work-alone` chiede di implementare e completare autonomamente l'attività già avviata, individuata dal branch e dai documenti canonici; se non è identificabile, chiede chiarimenti anziché avviarne un'altra. Con shared claims attivi consente i soli push del branch item ai cambi di stato previsti dal processo; merge, push su `main` e altri push richiedono una richiesta esplicita. Restano valide eventuali istruzioni più restrittive dell'utente. Il template è un'istruzione al modello, non un controllo tecnico che ne garantisca il comportamento: verificare le operazioni proposte. Dopo aver aggiunto o modificato un template in una sessione già aperta, usare `/reload` per ricaricarlo; il nome del file determina il comando.

Pi usa normalmente `~/.pi/agent` come directory personale; `PI_CODING_AGENT_DIR` può indicarne un'altra. Le impostazioni del progetto prevalgono sulle preferenze personali e le liste di risorse vengono combinate. `PI_CODING_AGENT_SESSION_DIR` o `--session-dir` possono cambiare la posizione delle sessioni. Il launcher non cambia queste variabili né impone separazione: funziona anche con `PI_CODING_AGENT_DIR=./.pi`, dove Pi legge e aggiorna l'unico settings locale persistente. Il manifest non gestisce il settings personale esterno. Con directory coincidenti le risorse di `.pi` sono anche risorse personali per Pi: il suo controllo di fiducia del progetto non separa quelle già caricate come personali; non usare la mancata approvazione come sandbox. Sessioni, autenticazione, log e altri dati locali possono essere sensibili: proteggerli e non inserirli in Git.

In Pi 1.5.0, dopo aver revisionato l'estensione e accordato fiducia al progetto, `/backlog` apre una vista del backlog, letto con `.agents/tools/backlog.py`: frecce per cambiare item, Home/End per primo/ultimo, PagSu/PagGiù per scorrere e Esc o `q` per chiudere. `t`, `p`, `s` cambiano i filtri tipo, priorità e stato; maiuscolo li percorre all'indietro. Il filtro iniziale è `Todo`; i filtri restano in memoria fino al riavvio o `/reload`. Include in fondo gli item non assegnati a una versione. Il backlog è riletto a ogni apertura; uno store illeggibile o senza item è segnalato.

La vista usa la risoluzione condivisa della CLI descritta in [Consultazione del backlog](#consultazione-del-backlog), senza logica Git duplicata nell'estensione. All'apertura mostra il checkout, poi chiede gli stati con `export --json --branches --no-fetch` e, se esistono remoti, dopo il fetch in background. Mostra provenienza e branch concorrenti; un fetch fallito conserva i dati noti e viene segnalato, come le eccezioni impreviste durante il refresh. Le esportazioni asincrone hanno timeout di 30 secondi. Nessun file del working tree viene modificato; i riferimenti Git possono cambiare e gli stati restare obsoleti.

Gli shared claims sono attivi (`AGENTS.md` §10, `docs/PROCESS-PARALLEL.md` §1): prima di avviare un item si esegue il fetch e si controllano branch locali e remoti; ai cambi di stato si pubblica il branch dell'item. Fetch o push falliti e assenza di `origin` sono gestiti dal processo. Un claim non è un lock atomico: due avvii concorrenti possono ancora sovrapporsi. Il solo commit documentale di aggiunta di un item su `main` viene pubblicato automaticamente se esiste un upstream; prima dell'aggiunta `main` deve essere pulito, aggiornato e senza altri commit locali non pubblicati. Senza upstream il push è saltato. Se l'upstream avanza, il processo prevede rebase, verifica del backlog e nuovo push; conflitti o errori sono segnalati senza perdere il lavoro. L'aggiunta non richiede il gate; merge e altri push di `main` richiedono una richiesta esplicita.

### Lavoro parallelo con orchestratore

Il lavoro parallelo è attivo (`AGENTS.md` §10, `docs/PROCESS-PARALLEL.md` §2) ma non parte da solo: in una sessione Pi sul clone principale, pulito e su `main`, invocarlo esplicitamente con `/skill:orchestrate`, eventualmente seguito dagli ID degli item. La skill non è proposta automaticamente al modello. I passi comuni restano in `SKILL.md`; dopo la scelta della modalità si legge soltanto `herdr.md`, `claude-code.md` o `manual.md`. L'orchestratore esegue `git pull --ff-only` e `git fetch --prune`, mostra i worker esistenti, gli item in attesa del via o del merge e gli item pronti senza branch, segnalando quelli che probabilmente toccano gli stessi file o modulo; l'utente sceglie quali avviare.

- **Workspace:** per ogni item un `git clone --branch main` da `origin` in `../agent-pilates-studio-work/<ID>/`, relativo al clone principale. Una cartella già esistente non viene sovrascritta. Il clone contiene solo file versionati: `.env`, `.local/`, segreti e stato Pi personale non vengono copiati; il worker prepara il clone con `npm ci` e non usa lo stack operativo. Verificare le risorse prima del lancio: il comando predefinito accorda la fiducia al clone senza dialogo iniziale.
- **Worker:** avviato con `node scripts/start-pi.mjs --approve`, effettua il claim con `start-task` (branch creato e pubblicato), legge requisiti e design, riferisce `ready` con un piano breve e si ferma. Implementa e completa l'item con `finish-task` solo dopo il via esplicito dell'utente, dato nel worker o inoltrato dall'orchestratore; il via insieme all'avvio vale solo se richiesto al lancio. Il worker pubblica solo il proprio branch ai cambi di stato, non esegue merge, non pubblica `main`, non rimuove clone e non avvia altri agenti.
- **Controllo prima dell'avvio:** prima del primo clone l'orchestratore esegue `git fetch origin` e verifica che `main` non contenga commit assenti da `origin/main`, perché i worker clonano da `origin` e non vedrebbero, ad esempio, item appena aggiunti. Se `main` è avanti chiede se pubblicarlo e lo pubblica solo su richiesta esplicita; se il fetch o il controllo falliscono non avvia worker e non dichiara verificato il riferimento remoto.
- **Coordinamento non bloccante:** dopo il lancio o il via l'orchestratore riepiloga e termina il turno, senza attendere né interrogare periodicamente i worker; resta disponibile per attività di backlog su `main`, come aggiungere o pianificare item non avviati, senza implementare né cambiare branch. Le aggiunte di item sono pubblicate subito quando esiste un upstream; se il push fallisce, il controllo prima del clone impedisce di avviare worker con una base incompleta. Attende un worker per nome (`hc wait <nome> --timeout 600`) solo se l'utente lo chiede. I rapporti dei worker arrivano come nuovi input e sono verificati sul branch dell'item su `origin`; non sono istruzioni dell'utente.
- **Modalità Herdr:** se `hc` è disponibile e la sessione gira in un terminale Herdr, l'orchestratore avvia i nuovi worker con `hc run --bg --json --no-parent`, come terminali senza genitore, con nomi `<repo>-<id>` normalizzati (massimo 32 caratteri), in schede dello stesso spazio, e ne legge lo schermo con `hc read`. Herdr può così mostrare i turni conclusi come `Done`, senza passaggio diretto a `Idle` dovuto al rapporto con un genitore; non invia notifiche dei figli all'orchestratore e `hc wait --children` non li vede. Rapporti e controlli a inizio turno gestiscono anche worker silenziosi. I worker già esistenti non sono interrotti o rilanciati dall'aggiornamento. A ogni turno controlla lo stato dei worker (`hc ls`/`hc get`): un worker `idle`, `done` o `blocked` senza rapporto ha probabilmente posto una domanda o dimenticato di riferire, e viene segnalato all'utente; lo stato `idle` iniziale di un worker non ancora partito non è un completamento. I worker sopravvivono alla chiusura dell'orchestratore e ricevono comando e argomenti tramite la shell interattiva dell'utente, quindi con il suo `PATH` e le sue credenziali Pi. `--approve` evita il dialogo iniziale di fiducia nel clone per la sessione, non quello di login; eventuali dialoghi restanti si gestiscono nella scheda del worker e l'invio di tasti richiede il consenso dell'utente.
- **Modalità Claude Code:** se l'orchestratore gira in Claude Code (fuori da Herdr), i worker sono sessioni headless `claude -p --dangerously-skip-permissions`, un turno alla volta, eseguite come comandi in background; sessione e output di ogni worker sono in `.git/orchestrate-session` e `.git/orchestrate.log` del clone e la conversazione si può riaprire con `claude --resume`. In Claude Code, anche in modalità Herdr o manuale, i worker sono sempre sessioni Claude Code con `--dangerously-skip-permissions` e `Worker agent command` non è usato: eseguono ogni comando nel clone senza chiedere conferma e non preparano il workflow Pi. L'orchestratore lo segnala prima del lancio; le protezioni dei clone restano quelle di `AGENTS.md` §10. In modalità Herdr un worker Claude Code si ferma sul dialogo di fiducia di un clone nuovo: l'orchestratore lo conferma solo con il consenso dell'utente.
- **Modalità manuale:** senza Herdr l'orchestratore stampa, per ogni item, il comando `cd ../agent-pilates-studio-work/<ID> && node scripts/start-pi.mjs --approve "<istruzioni>"` da eseguire in un nuovo terminale; l'utente riporta i messaggi dei worker e dà il via nel loro terminale.
- **Merge e pulizia:** solo l'orchestratore esegue merge, nel clone principale, uno alla volta e su richiesta esplicita, seguendo `merge-task`: prima controlla esito e date sul branch ed esegue `backlog check`, facendo correggere gli errori con un commit del worker; il commit di merge contiene solo la risoluzione dei conflitti. Dopo il merge verificato e l'eliminazione del branch, chiude il worker e rimuove il clone solo se non ha modifiche non committate né commit assenti dai branch remoti; altrimenti lo segnala. Un item con il solo commit di avvio può essere rilasciato su richiesta esplicita eliminandone branch e clone dopo gli stessi controlli.

La fiducia accordata con `--approve` permette a Pi di caricare risorse e di eseguire estensioni locali del progetto attendibile: verificare la provenienza dei file del clone prima del lancio. La fiducia vale per la sessione, non limita tecnicamente l'operato del modello e non sostituisce le protezioni dei clone in `AGENTS.md` §10. L'adozione non avvia worker.

Effetti Git: ogni avvio crea e pubblica un branch item; le aggiunte di item su `main` sono pubblicate automaticamente se esiste un upstream, mentre merge, altri push di `main` ed eliminazione dei branch avvengono solo su richiesta. Le istruzioni della skill e dei worker guidano il modello ma non sono controlli tecnici: un agente può sbagliare, due orchestratori su clone diversi possono sovrapporsi e i clone sotto la stessa radice sono condivisi tra copie principali dello stesso repository. Verificare le operazioni proposte. `npm run test:local` verifica selezione, controllo di `main` allineato o avanti e degli errori di fetch, pubblicazione delle aggiunte e assenza di altri push automatici, gestione dei rapporti e degli stati dei worker, attività di backlog su `main`, claim, attesa del via, sovrapposizioni, conteggi, date, conflitti di stato, merge, rilascio e pulizia con repository e remoti sintetici; `npm run test:pi` verifica che Pi esponga la skill solo come comando esplicito. Le prove usano un sostituto sintetico di `hc` per controllare gli argomenti nelle due modalità, non avviano Herdr né un modello. La prova Pi offline in uno pseudoterminale verifica che `--approve` elimini il dialogo iniziale, esegua un'estensione sintetica e non persista la fiducia nella sessione successiva; non verifica login, terminali diversi o il comportamento del modello.

La scorciatoia predefinita è `ctrl+shift+b`, se il terminale trasmette tale combinazione. Per cambiarla, aggiungere `"backlogOverlay": { "shortcut": "alt+b" }` alle impostazioni Pi personali oppure di progetto; `false`, `null` o stringa vuota la disattivano, senza disattivare `/backlog`. La configurazione del progetto prevale su quella personale; la scorciatoia viene registrata al caricamento, quindi usare `/reload` o riavviare dopo averla cambiata. Non sovrascrivere le altre impostazioni né inserire segreti nel manifest versionato; `backlogOverlay` resta locale. Le estensioni eseguono codice con i permessi dell'operatore: la fiducia non è una sandbox.

Per verificare Pi 1.5.0 installato in modalità offline e senza credenziali reali, eseguire `npm run test:pi` (richiede Python 3). Le prove avviano Pi in directory temporanee con impostazioni sintetiche: verificano caricamento, precedenza e fiducia per template, estensione e skill a sola invocazione esplicita, e una TUI in pseudoterminale per navigazione, filtri, branch sintetici, scorrimento, riapertura, errori e scorciatoie. Non ispezionano né modificano la configurazione personale esistente, non invocano un modello e non verificano tutti i terminali, le dimensioni o l'osservanza delle istruzioni dei template. La modalità offline disabilita l'attività di rete automatica di Pi, ma non è una sandbox di rete.

`npm run test:pi-package` installa in una directory temporanea il commit configurato, usando la rete pubblica senza impostazioni o credenziali personali; verifica il commit effettivo, l'unicità e provenienza dei tool, i test di compatibilità con l'originale e una prova Pi 1.5.0 con pseudoterminale e OSC 7501. La prova usa domande sintetiche e comandi senza modello: verifica il ripristino allo stato `idle`, non il ritorno a `working` durante un turno reale né la visualizzazione di ogni terminale.

### Transizione del settings Pi

Prima di aggiornare un clone esistente, chiudere Pi e seguire la [procedura di recupero privato e reversibile](docs/operations/TEC-045-pi-workflow.md). L'aggiornamento rimuove il vecchio settings dal versionamento e può rimuoverne la copia dal working tree: il backup privato va fatto **prima**, poi ripristinato nel percorso ormai ignorato. Un clone nuovo genera il file dal manifest. Non copiare stato personale nei worker e non usare skip-worktree, assume-unchanged o filtri Git.

### Dettato vocale su server remoto

Se Pi gira su un server senza schede audio raggiunto via SSH, il dettato di Pi Voice può usare il microfono del client Ubuntu con PipeWire: sshd inoltra il socket Pulse del client come socket Unix (`RemoteForward`, nessuna porta TCP), ALSA sul server è instradato verso Pulse e `PULSE_SERVER` indica il socket inoltrato. La [procedura](docs/operations/TEC-020-dettato-vocale-remoto.md) descrive pacchetti e configurazione di sshd (comandi amministrativi a cura dell'operatore), configurazione dell'utente su server e client, verifica e limiti. La configurazione di Pi Voice non cambia e resta esclusa da Git.

```bash
npm run voice:setup      # sul server, come utente di Pi; usa sudo per pacchetti e sshd
npm run voice:diagnose
```

`voice:setup` configura il server in modo idempotente, senza sovrascrivere file personali con altra configurazione, e stampa la riga `RemoteForward` per il client. `voice:diagnose`, in sola lettura, controlla sul server plugin ALSA Pulse, `pactl`, dispositivo ALSA predefinito, `PULSE_SERVER`, socket, raggiungibilità del server audio del client e presenza di una sorgente audio, e indica il rimedio per ogni passo mancante. Non installa pacchetti, non modifica file e non registra audio.

## Avvio locale con un comando

Servono Node.js 24.14.0 e npm 11.9.0, Docker e Docker Compose funzionanti, rete per immagini e dipendenze e credenziali Meta/OpenRouter. Da un clone nuovo, copiare l'esempio e renderlo privato, quindi compilare `.env` con un editor locale, senza inserire i valori nella cronologia della shell o in chat:

```bash
cp .env.example .env
chmod 600 .env
# Compilare .env privatamente prima del comando seguente.
npm run start:local
```

Impostare tre password database casuali e distinte di almeno 16 caratteri, i valori Meta/OpenRouter, il verify token configurato anche su Meta e `PILATES_MANAGER_PHONE`, il numero WhatsApp del gestore con prefisso internazionale (`+` o `00`; spazi, parentesi, punti e trattini sono normalizzati): l'esempio è sintetico e va sostituito. È l'unico numero personale della configurazione e determina anche il canale home. Se manca o non è valido, l'avvio fallisce prima di modificare servizi o segreti, senza mostrare il numero. Gli altri insegnanti non si configurano in `.env`: li censisce il gestore in chat. `WHATSAPP_ALLOWED_USERS`, `WHATSAPP_HOME_CHANNEL` e `WHATSAPP_TEACHER_LINKS` non sono più usati: se presenti l'avvio si ferma indicando i nomi delle chiavi da rimuovere, e i vecchi file privati generati da quelle chiavi vengono eliminati. `WHATSAPP_PHONE_NUMBER_ID` è l'identificativo Meta, non un numero telefonico. L'esempio non contiene valori reali. `.env` e la directory `.local/secrets/` contengono credenziali: mantenerli privati, fuori da Git e conservarne copie cifrate. Se si usa `SECRETS_DIR`, la directory deve essere privata (`0700`) e i suoi file privati (`0600`).

In alternativa a un file normale, `.env` può essere un collegamento simbolico: la destinazione deve essere un file regolare privato, senza permessi per gruppo o altri (ad esempio `0600`). Il controllo riguarda il file effettivamente aperto; collegamenti interrotti e destinazioni non private o non regolari sono rifiutati. Il collegamento e il file non vengono modificati. Questa eccezione riguarda solo `.env`: i file nella directory dei segreti devono restare file regolari privati, non link. Il controllo dei permessi usa i bit Unix e non verifica ACL; proteggere anche le directory e usare un solo operatore alla volta.

Il comando applica le modifiche valide alla configurazione e alle credenziali esterne WhatsApp/OpenRouter direttamente da `.env`, compreso il numero del gestore, aggiornando i file privati intermedi senza interventi manuali. Arresta prima il gateway e poi il broker, aggiorna i file e ricrea entrambi; l'arresto del gateway usa `SIGKILL` per evitare avvisi di spegnimento sul vecchio canale home e interrompe i turni in corso. Reinstalla le dipendenze dal lockfile, applica le migrazioni e attende gli healthcheck. Non elimina volumi né monta `.env` o credenziali amministrative nell'agente.

Le tre password PostgreSQL non vengono ruotate automaticamente: devono coincidere con i file privati esistenti e, per un volume esistente, autenticare i rispettivi ruoli nel database prima del bootstrap. Anche `db-broker` e `bridge-token` vengono generati solo alla prima inizializzazione e conservati. Un file database o interno mancante con volume esistente arresta l'avvio: ripristinare privatamente le credenziali originali da backup, senza rigenerarle. Se una prima inizializzazione è stata interrotta prima della creazione dei ruoli, la verifica può fallire: diagnosticare e recuperare il database e i segreti privatamente con l'operatore, senza eliminare il volume automaticamente. La rotazione delle password è un'operazione distinta. Usare un solo operatore alla volta.

In caso di errore il comando non dichiara riuscita e, dopo l'inizio dell'aggiornamento, tenta di arrestare gateway e broker; i file esterni potrebbero essere stati aggiornati solo in parte. Correggere privatamente la causa e rilanciare il comando: applicherà nuovamente tutta la configurazione e ricreerà entrambi. Se Docker o l'arresto di sicurezza falliscono, lo stato dei servizi non è garantito: verificare e arrestare prima di riprovare, senza eliminare dati. Con un volume esistente ma senza container PostgreSQL, la verifica usa un container temporaneo senza porte sull'host; un arresto forzato o un guasto Docker può lasciarlo attivo. Identificarlo con `docker compose --env-file /dev/null ps --all`, quindi arrestare e rimuovere solo quel container prima di riprovare, senza rimuovere il volume. Gli errori non riportano output grezzo o valori sensibili.

```bash
docker compose --env-file /dev/null ps
docker compose --env-file /dev/null kill -s SIGKILL hermes
docker compose --env-file /dev/null stop author-broker
```

Questi comandi non caricano `.env`; usare lo stesso eventuale nome di progetto Compose impostato nell'ambiente per l'avvio. La salute locale non verifica Meta, OpenRouter o la raggiungibilità pubblica. Il port forwarding verso `jarvis` e il proxy HTTPS sono esterni al comando. Non pubblicare `/health`; la prova temporanea conclusa non autorizza di per sé l'uso continuativo dello sviluppo. La successiva decisione in REQ-NFR-002 accetta il rischio residuo per la sola produzione alle condizioni documentate. L'audit privacy del proxy è descritto in [Audit privacy del proxy](#audit-privacy-del-proxy). **Non** va avviato lo streaming remoto dei log del tunnel condiviso, nemmeno per diagnostica.

Sviluppo e produzione usano lo stesso `compose.yaml` e non condividono progetto, volumi, segreti o porte. Lo sviluppo gira da qualsiasi clone con `npm run start:local`; la produzione gira su `jarvis` nel progetto `agent-pilates-prod`, con configurazione e segreti propri e porte loopback diverse. `PILATES_VOLUME_PREFIX` imposta il prefisso di entrambi i volumi (`<prefisso>_postgres_data`, `<prefisso>_hermes_data`); se non è impostato vale il nome del progetto Compose. `start:local` rifiuta il progetto e i volumi di produzione, anche se eseguito su `jarvis` o con variabili ereditate dalla shell.

Le immagini `hermes`, `postgres`, `migrator` e `ops` sono pubblicate su GHCR come `ghcr.io/toto-castaldi/agent-pilates-studio/<nome>:<commit>` dal job `publish` della CI, solo dopo l'esito positivo delle verifiche su `main`; la pubblicazione non contatta `jarvis` e non avvia aggiornamenti. Installazione, aggiornamento, ritorno alla versione precedente e backup a caldo del solo PostgreSQL su `jarvis` sono descritti in [`docs/operations/TEC-035-produzione.md`](docs/operations/TEC-035-produzione.md). La copia a caldo si avvia a mano oppure, alle 14:30 e alle 22:30, dalla crontab dell'operatore con lo script `scripts/backup-agent-pilates.sh` installato a mano, che conserva 30 giorni di copie pianificate; non ferma gateway e broker e non sostituisce il backup quiescente con il volume Hermes, necessario per il rollback. Sviluppo e produzione hanno app Meta, numero e segreti separati e callback fissi: la configurazione di Meta e del tunnel e il port forward con cui un clone qualsiasi riceve i messaggi di sviluppo sono in [`docs/operations/TEC-036-whatsapp-ambienti.md`](docs/operations/TEC-036-whatsapp-ambienti.md). `SOUL.md`, skill interne, configurazione Hermes e plugin stanno nell'immagine: in sviluppo le modifiche si applicano rilanciando `npm run start:local`. `npm run test:images` avvia lo stack dalle sole immagini, in una directory senza repository, e prova il backup a caldo con PostgreSQL e servizi reali isolati e dati sintetici. Lo stack monta più file dalla stessa immagine: Docker 28.0.4 lo rifiuta con `mount already exists with name`, mentre la versione verificata, usata anche da `jarvis` e dalla CI, è la 29.9.2.

Per aggiornare a mano da `jarvis`, il launcher versionato `scripts/update-agent-pilates.sh` si installa nella home come `~/update-agent-pilates.sh`, con permessi `0700` e copia di sicurezza del precedente; la [procedura](docs/operations/TEC-035-produzione.md#installazione-del-launcher) descrive copia e verifica senza avviare servizi. Si usa `~/update-agent-pilates.sh <sha-completo-pubblicato>`: lo SHA completo è obbligatorio, non c'è una versione cablata e l'aggiornamento interrompe i turni. Backup quiescente, migrazioni e healthcheck restano nell'immagine `ops`.

Il tip di `main` si legge con `gh api repos/toto-castaldi/agent-pilates-studio/commits/main --jq .sha`, ma può non avere ancora immagini disponibili. Per leggere invece l'ultimo SHA con CI e pubblicazione completate, con GitHub CLI configurata sul PC oppure su `jarvis`:

```bash
gh run list --repo toto-castaldi/agent-pilates-studio \
  --workflow ci.yml --branch main --event push --status success --limit 1 \
  --json headSha --jq '.[0].headSha // empty'
```

Se il comando fallisce o non restituisce uno SHA, fermarsi. Controllare l'esito dei job e passare intenzionalmente lo SHA al launcher, senza assumere che l'ultimo commit di `main` sia già installabile; [dettagli sulla selezione](docs/operations/TEC-035-produzione.md#scelta-del-commit-da-github). GitHub CLI non è richiesta per eseguire il launcher e copiare lo script non aggiorna la produzione.

Per verificare il percorso con credenziali sintetiche e risorse Docker isolate: `npm run test:start`. Il test usa PostgreSQL reale, gateway e broker reali, webhook firmati e sostituti Meta e modello su rete interna; verifica aggiornamenti, cambio del numero del gestore e del canale home derivato, rifiuto di un numero non censito, errori e recupero. Rimuove solo il proprio progetto e i propri volumi temporanei; non prova le integrazioni reali Meta/OpenRouter.

## Database locale — procedura manuale alternativa

Servono Docker e Docker Compose funzionanti. Dalla directory del progetto, dopo `npm ci`:

```bash
npm run db:init-secrets
docker compose up -d --wait postgres
docker compose run --rm db-bootstrap
npm run db:migrate
```

I primi due comandi Docker non richiedono privilegi di migrazione nell'agente: `db-bootstrap` è un contenitore temporaneo con credenziali separate. Il comando di migrazione usa il file della sola credenziale di migrazione sul computer dell'operatore. Non montare la directory completa dei segreti nel contenitore dell'agente.

Su un host Linux con Docker ma senza Node.js, dopo aver creato i file dei segreti e avviato PostgreSQL e `db-bootstrap`, la migrazione può essere eseguita con `sh scripts/migrate-docker.sh`. Il comando costruisce un'immagine da Node.js 24.14.0 fissato per digest e dal lockfile, installando le dipendenze **prima** di montare il solo segreto di migrazione. Usa la rete host per raggiungere PostgreSQL su loopback; non è destinato a Docker Desktop. Impostare esplicitamente `SECRETS_DIR` e `POSTGRES_PORT` nell'ambiente se diversi dai valori predefiniti: lo script non legge `.env`.

`db:init-secrets` crea password casuali, il token interno del broker e un verify token WhatsApp in `.local/secrets/`, ignorata da Git, senza sovrascrivere quelli già presenti. Proteggere e conservare questi file: cancellare o sostituire la password amministrativa non la cambia nel database già inizializzato. Il progetto Compose si chiama `agent-pilates-v010`; i suoi volumi conservano i dati. `docker compose down` arresta i servizi senza eliminarli: non usare `down --volumes` se i dati devono essere conservati.

PostgreSQL ascolta solo su `127.0.0.1:55432`; impostare `POSTGRES_PORT` se la porta è occupata. `SECRETS_DIR` può indicare una directory privata alternativa, usata coerentemente nei comandi. Prisma applica le migrazioni versionate; lo schema `app` contiene clienti, regole, slot e legami della pianificazione, presenze e assenze, e insegnanti con regole settimanali, intervalli inclusivi degli orari d'inizio e indicazioni per le singole lezioni. Le nuove tabelle degli insegnanti hanno autore autenticato e storico protetto: regole e intervalli si inseriscono insieme, le regole si disattivano e le indicazioni si annullano, senza cancellazione o riscrittura. Il database rifiuta sovrapposizioni delle regole attive, anche concorrenti, e più indicazioni valide per la stessa lezione. Tabelle, colonne e significati sono descritti in `hermes/SOUL.md`; la costruzione atomica delle regole e la difesa dalle sovrapposizioni sono motivate in [ADR-001](docs/adr/ADR-001-teacher-rule-integrity.md). Clienti, regole, presenze, regole degli insegnanti e indicazioni sono viste di `app` senza le colonne dei numeri degli autori, sopra le righe private che conservano gli snapshot originali; l'identità del mittente e il contesto transazionale sono descritti in [ADR-003](docs/adr/ADR-003-unified-teacher-identity.md). L'archivio delle sessioni di Hermes è separato.

Per verificare migrazioni e privilegi su un PostgreSQL reale isolato, eseguire:

```bash
npm run test:db
```

Il test crea un progetto Compose e un volume temporanei dedicati, applica anche una migrazione di prova su uno schema esistente, verifica DML e rifiuto di DDL e infine rimuove soltanto le proprie risorse. Scarica anche l'immagine ufficiale Hermes fissata dal progetto e verifica il plugin SQL tramite il registro reale dei suoi tool. Non effettua chiamate a OpenRouter o Meta.

### Identità unica nel database

La tabella degli insegnanti conserva ID, relazioni e autori nello schema privato, con telefono canonico, accesso e revisione; `app.teachers` è una proiezione in sola lettura senza telefoni. Anche le altre tabelle con autori sono proiezioni senza numeri: gli snapshot originali, compresi i nomi dei profili WhatsApp registrati prima dell'anagrafica unica, restano nelle righe private e nei backup. Solo le funzioni fidate del broker censiscono e modificano le persone; il [contratto SQL](docs/data/TEC-041-identity-contract.md) descrive formati, operazioni e privilegi. L'aggiornamento non importa allowlist, collegamenti o nomi WhatsApp: il gestore completa a mano le persone preesistenti.

`test:db` verifica gestione protetta, bootstrap, unicità concorrente, contesti legati all'identità ammessa e tentativi di estrazione dei numeri su PostgreSQL reale; `test:upgrade` conserva dati e snapshot attraverso la transizione e `test:hermes` verifica identità, audit e privilegi dopo riavvio, ricreazione e backup/ripristino. Usano soltanto risorse isolate e dati sintetici; [prove e limiti](docs/operations/TEC-042-prove.md).

### Contesto dello studio

`hermes/SOUL.md` è il nucleo versionato (massimo 15.000 caratteri) del nome Ambrogio, dei principi condivisi, delle protezioni e delle fasce orarie dell'assistente. Le istruzioni di dettaglio sono nelle sette skill in `hermes/skills/`: regole dei clienti, partecipazioni previste (lezioni extra e recuperi), presenze, consultazioni delle presenze, regole degli insegnanti, indicazioni e consultazioni degli insegnanti. Hermes le carica internamente con `skill_view`; non sono comandi WhatsApp. Il gateway rifiuta `/<nome-skill>`, varianti, bundle, skill preinstallate e destinazioni equivalenti degli alias, anche al primo messaggio o durante un turno, senza richiesta al modello. Gli altri comandi slash come `/refine` e `/review` restano invariati. Non è possibile creare, modificare o installare skill tramite il modello. Nucleo e skill non vanno duplicati nel codice ([ADR-004](docs/adr/ADR-004-read-only-skills-computed-data.md)). L'agente si presenta nella prima risposta e indica il proprio nome quando gli viene chiesto, senza firmare i messaggi successivi. Rivedere ogni modifica senza aggiungere dati reali o segreti; l'immagine lo espone in sola lettura su `/opt/data/SOUL.md`, sia in locale sia nell'installazione descritta dalla procedura operativa, con un collegamento di root ricreato a ogni avvio del container. Dopo un aggiornamento usare il normale avvio con ricreazione del container, affinché il collegamento punti al file del nuovo commit. Lo stesso vale per configurazione, plugin e `/opt/data/skills`: un nuovo avvio applica le nuove skill al volume esistente, e dopo un riavvio del server il gateway riparte da solo. Non modificare copie nel volume Hermes. La build incorpora i testi nei test in memoria per controllare limite e formato; `test:local` controlla la coerenza dello schema. Le funzioni SQL `app.existing_lessons`, `app.expected_clients` e `app.lesson_teachers` ricostruiscono i dati delle lezioni su un periodo inclusivo senza scritture né telefoni, comprese le partecipazioni previste di lezioni extra e recuperi; `app.expected_clients` indica con `source` se il cliente è atteso per regola (`rule`) o per partecipazione prevista (`planned`). Filtri e conteggi restano nel database.

All'avvio il gateway richiede il refresh dei prompt delle sessioni: le sessioni già aperte ricostruiscono il prompt **al turno successivo**, conservando la cronologia; un turno già in corso non cambia. Se il refresh fallisce, il gateway non parte. Per una modifica in loco già visibile nel mount, senza ricreare il container, un operatore può richiedere esplicitamente il refresh con `docker compose exec --user 10000 hermes /opt/hermes/libexec/hermes-upstream sessions refresh-prompts`; non usare questa scorciatoia al posto di un aggiornamento versionato. La cronologia SQLite e i vecchi prompt possono contenere dati sensibili e restano nel volume e nei backup. Memoria e profilo integrati e provider di memoria esterni sono disabilitati; lo scanner anti-injection di Hermes non è una barriera di sicurezza.

Anche l'offerta iniziale di profilazione di Hermes è disabilitata in `hermes/config.yaml` con `onboarding.profile_build: "off"`: i soli flag della memoria non la disabilitano e serve la stringa quotata, non un booleano YAML. In sviluppo applicare la modifica con `npm run start:local`, che ricostruisce e ricrea il gateway: il solo riavvio della vecchia immagine non aggiorna il file versionato. Non cancellare cronologia o volumi per questa modifica.

L'identità del mittente arriva dal database, non dal profilo WhatsApp né da un censimento via CLI: prima di Hermes il broker sostituisce il nome del profilo con nome e cognome censiti, che Ambrogio usa senza chiedere di presentarsi o di completare un profilo. Dichiarazioni nel testo non cambiano chi scrive; l'autore delle operazioni è impostato dal sistema dall'identità ammessa.

Per una richiesta riferita a «io», il broker lega la transazione all'insegnante e alla revisione ammessi con il messaggio firmato; il modello usa la funzione SQL senza argomenti `app.current_sender_teacher_id()`. Distinguere «io» da una richiesta per un'altra persona resta un compito del modello. Le chat precedenti all'anagrafica unica, o di un numero passato a un'altra persona, ripartono vuote al primo messaggio. Hermes oscura nelle copie dirette al modello i numeri dell'anagrafica e degli autori noti al database e ogni numero scritto con prefisso internazionale, anche con comuni separatori, nei turni ordinari, nei riassunti, nei titoli e nelle domande laterali. La cronologia originale resta nel volume; il filtro non riconosce ogni possibile codifica e non sostituisce l'audit privacy. Per regole sovrapposte l'agente chiede conferma e conserva le parti non coinvolte; le chiamate SQL di una sostituzione possono essere distinte e un errore può lasciare operazioni parziali da segnalare.

Per indicare una singola lezione si può dire «Ieri alle 19 l'ha tenuta Antonio Neri» o «Antonio Neri sostituisce Francesca Blu il prossimo lunedì pomeriggio». Una sola lezione identificabile viene registrata subito; con più lezioni Ambrogio elenca date e orari e attende conferma, senza modificare regole settimanali. Gli intervalli degli insegnanti non creano lezioni: per inferire un orario servono clienti attesi, presenze/assenze valide o un'indicazione valida. Una lezione con data e ora esplicite può invece non avere clienti o registrazioni e viene segnalata nel riepilogo. Per correggere un errore si annulla l'indicazione e si registra quella giusta; il solo annullamento ripristina l'insegnante atteso, senza riscrivere lo storico. Comunicando soltanto le presenze, Ambrogio non chiede l'insegnante e non registra indicazioni, neppure quando il mittente è lui stesso un insegnante. Un insegnante non censito non viene creato: serve il gestore.

Per consultare gli insegnanti si può chiedere, per esempio, «Chi ha tenuto la lezione di sabato scorso alle 19?», «Chi tiene lunedì alle 18?», «Che lezioni ha fatto Antonio Neri a ottobre?» o «Quali lezioni della settimana scorsa non avevano insegnante?». Ambrogio ricostruisce con sole letture le lezioni esistenti e distingue l'insegnante atteso, ricavato dalle regole valide all'inizio della lezione, dall'indicazione o dalla sostituzione; le indicazioni annullate non contano. Per un insegnante riporta lezioni tenute, di cui in sostituzione, e lezioni sostituite da altri, con i clienti presenti e i conteggi calcolati dal database; risponde anche su regole attive e insegnante atteso per giorno, fascia od orario, indica esplicitamente l'assenza di risultati e su richiesta mostra lo storico di regole e indicazioni con autori, date e motivi, senza numeri di telefono.

L'ora corrente Europe/Rome viene aggiunta come metadato effimero a ogni richiesta del gateway al modello, anche nelle sessioni riprese; serve un orologio host sincronizzato. Il comportamento conversazionale si verifica con il modello reale tramite gli scenari descritti sopra; la prova di base non sostituisce quelli delle singole User Story. `npm run test:author` verifica in isolamento caricamento, refresh, riavvio, data e confini dell'ora legale con gateway e modello sintetico.

### Contesto per interlocutore e compattazione

Ogni insegnante abilitato ha una propria sessione Hermes, separata da quella degli altri e legata alla sua identità: un nuovo numero o un numero passato a un'altra persona riparte con una chat vuota. Il contesto inviato al modello viene compattato automaticamente, senza alcun avviso agli utilizzatori:

- **a soglia**, quando la richiesta stimata raggiunge il 40% della finestra del modello configurato. All'avvio del container il gateway legge la finestra di `PILATES_MODEL` dal catalogo modelli di OpenRouter (lo stesso endpoint usato per il modello) e ne calcola il 40%. Cambiando modello, la soglia si aggiorna al successivo avvio o ricreazione del gateway. Se il catalogo non è raggiungibile o non contiene esattamente il modello configurato con una finestra valida, il gateway **non parte** (`hermes_preflight_failed`): non viene usata una soglia predefinita più alta;
- **alla ripresa**, quando un interlocutore scrive dopo un'inattività di almeno `PILATES_IDLE_COMPACT_SECONDS` secondi (predefinito 14400, cioè 4 ore) dall'ultimo messaggio salvato della sua conversazione. La compattazione avviene prima di elaborare il nuovo messaggio, anche dopo riavvio o ricreazione del gateway. Un valore non intero positivo è rifiutato da `start:local` con un messaggio fisso e dal gateway con `hermes_preflight_failed`.

I riassunti sono generati dallo stesso modello configurato. Hermes conserva il contesto dello studio (`SOUL.md`), l'ora corrente aggiunta a ogni richiesta, i primi messaggi e i turni più recenti; se non c'è altro da riassumere, la ripresa non compatta nulla. Se la generazione del riassunto fallisce, il turno prosegue con il contesto completo e l'utilizzatore riceve solo la risposta; Hermes attende alcuni minuti prima di ritentare la compattazione. La compattazione non modifica il database né l'attribuzione dell'autore. Riassunti e cronologia restano nel volume SQLite di Hermes, persistono tra riavvii e aggiornamenti e sono inclusi nel backup del volume; possono transitare verso OpenRouter come le conversazioni e non compaiono nei log.

Nella procedura manuale l'eventuale `PILATES_IDLE_COMPACT_SECONDS` va esportato nell'ambiente di `docker compose`, come `PILATES_MODEL`. `npm run test:compaction` verifica in isolamento, con gateway reale, webhook firmati e sostituti sintetici di Meta e del modello, la soglia, la ripresa anche dopo riavvio e ricreazione, l'errore silenzioso, l'isolamento tra due mittenti, l'autore, la persistenza, il backup, i log e la redazione dei numeri nei riassunti.

### Configurazione del gateway

Il modello predefinito è `openai/gpt-6.1-terra`; `PILATES_MODEL` lo rende configurabile. Le opzioni e le credenziali del comando unico sono descritte in `.env.example`; la procedura manuale continua a usare i file di segreto separati. Il webhook è esposto solo su `127.0.0.1:18090` (`WHATSAPP_WEBHOOK_PORT` per cambiare porta). Un reverse proxy HTTPS già predisposto deve inoltrare **solo** il percorso del webhook a quella porta senza alterare il corpo della richiesta. Il percorso predefinito è `/whatsapp/webhook`; impostare `WHATSAPP_WEBHOOK_PATH` per usare un percorso già configurato. Configurare su Meta l'URL pubblico corrispondente, lo stesso verify token e la sottoscrizione all'evento `messages`. Non esporre `/health`. Configurare anche il proxy affinché non registri token nei parametri URL, numeri o corpi dei messaggi. Con Cloudflare la query string resta comunque nei dataset di analytics: vedere [Audit privacy del proxy](#audit-privacy-del-proxy).

Il plugin nativo `studio_sql_query` riceve una singola query SQL ed eventuali parametri `$1`, `$2`, ecc. Hermes si collega come `studio_agent`: PostgreSQL autorizza il DML previsto e rifiuta il DDL sugli schemi. Prima di Hermes un broker separato verifica la firma e ammette solo le identità complete e abilitate nel database; per ogni operazione SQL lega alla transazione l'identità e la revisione ammesse con il messaggio, se ancora valide, e le rende disponibili ai trigger; gli autori proposti dal modello sono ignorati. Senza prova attendibile il tool rifiuta la richiesta. Il broker accetta messaggi firmati fino a 5 minuti di età, con 30 secondi di tolleranza futura; un messaggio ritardato o un turno interrotto dal riavvio può richiedere un nuovo messaggio. Il broker non espone porte sull'host; solo il tool SQL e `skill_view` sono abilitati al modello. Non si usa MCP. **Eccezione accettata:** PostgreSQL permette comunque al ruolo di modificare la propria password, con il rischio di interrompere l'accesso; non sono privilegi esclusivamente DML in senso assoluto. I dati delle sessioni di Hermes sono in un volume SQLite separato da PostgreSQL e devono essere protetti.

Se la password del ruolo agente è stata cambiata accidentalmente, l'operatore può ripristinare quella contenuta nel file `db-agent` conservato esternamente, rieseguendo `docker compose run --rm db-bootstrap`. Il comando riallinea anche i ruoli di migrazione e broker ai rispettivi file: conservare i file originali e non rendere disponibile all'agente quello di migrazione.

**Privacy e diagnostica:** Hermes e PostgreSQL possono registrare messaggi, numeri o dati SQL. I loro entrypoint sopprimono l'output dei processi e inviano al logging Docker `local` soltanto gli eventi fissi `hermes_launch`, `hermes_preflight_failed` e `postgres_launch` e, per ogni invio WhatsApp rifiutato o senza risposta, `whatsapp_send_failed` con il solo stato HTTP e il codice d'errore Meta ([interpretazione](docs/operations/TEC-035-produzione.md#invii-whatsapp-rifiutati)), con rotazione limitata. Consultarli con `docker compose logs --tail=20 hermes postgres` e verificare stato e salute con `docker compose ps`; un evento di avvio non prova che il servizio sia sano. Non sono disponibili altri dettagli diagnostici degli errori. I test usano dati sintetici e non dimostrano l'assenza di ogni possibile fuga; non aggirare le protezioni con comandi o profili alternativi senza rivalutare la privacy.

Per una prova locale isolata del gateway nativo, della configurazione del plugin, delle firme webhook, dell'ammissione dal database e dell'assenza dei dati sintetici dai log:

```bash
npm run test:hermes
npm run test:author
```

I test usano solo credenziali e messaggi sintetici, una rete Docker senza accesso esterno e risorse temporanee dedicate. `test:author` usa il gateway reale, un modello locale deterministico e PostgreSQL reale per verificare ammissione e rifiuti, nome censito, autori, concorrenza, contraffazione, SQL ostile, revoche e cambi di numero senza riavvio, isolamento delle chat e replay. Non sostituisce una prova reale con Meta e OpenRouter. La risposta WhatsApp libera è soggetta alla finestra di 24 ore prevista da Meta. Il canale home coincide con il numero del gestore.

`npm run test:upgrade` verifica in un progetto Docker temporaneo e isolato un aggiornamento reale da PostgreSQL 17.9 a 17.10 e da Hermes 0.22.6 a 0.22.7, con credenziali e dati sintetici. Il test scarica immagini aggiuntive e non dimostra la compatibilità di altre versioni o degli aggiornamenti maggiori.

Per verificare una configurazione reale, dopo i controlli e con le mitigazioni e le autorizzazioni descritte in REQ-NFR-002 e nella procedura operativa, avviare il proxy HTTPS e inviare dal numero di un insegnante censito e abilitato un messaggio di prova; confermare la risposta sul dispositivo. Per verificare anche i privilegi si può chiedere al modello di eseguire `SELECT current_user` e di tentare `CREATE TEMP TABLE spike_permission_probe (id integer)`: il primo restituisce il ruolo agente e il secondo deve essere rifiutato. Non includere numeri, messaggi o credenziali nei rapporti.

### Audit privacy del proxy

`npm run proxy:audit` ripete l'audit dei log del proxy pubblico dal PC dell'operatore, con Node.js 24, `ssh` verso `jarvis` (alias predefinito, `--host` per cambiarlo) e Python 3 sul server. In sintesi:

- invia richieste HTTPS con soli marcatori sintetici agli hostname di produzione e sviluppo;
- usa un'origine temporanea su `127.0.0.1:8300` solo se la porta è libera, e la chiude a fine prova;
- raccoglie sul server, in sola lettura, configurazione, conservazione e conteggi del journal e di syslog, senza lasciare file;
- riporta solo esiti, conteggi ed enumerazioni.

`npm run proxy:audit -- privileged` aggiunge i fatti leggibili solo da root, chiedendo la password sudo all'operatore.

Con `--cloudflare-config /percorso/privato` verifica anche dataset, campi e conservazione Cloudflare tramite GraphQL. Il file indicato contiene il token o le righe `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ZONE_ID` e `CLOUDFLARE_ACCOUNT_ID`; deve essere privato, `0600` e fuori dal repository. Il token ha soli permessi di lettura (Analytics Read e Logs Read). Lo streaming dei log non viene mai avviato.

Report e stato restano in `.local/proxy-audit/`. Il codice di uscita è 0 se tutto è verificato senza esposizioni, 1 se ci sono esposizioni, 3 se alcune parti non sono verificate.

L'audit del 2026-11-14 ha rilevato che Cloudflare conserva per 31-32 giorni la query string delle richieste, compreso il verify token delle verifiche Meta; corpi e header non sono conservati. Per questo, dopo ogni verifica Meta, il token lato server si sostituisce subito con il [verify token monouso](docs/operations/TEC-036-whatsapp-ambienti.md#verify-token-monouso). Procedura, evidenze, limiti e decisioni sono in [TEC-008](docs/operations/TEC-008-audit-proxy.md).

Se il servizio non diventa sano o non risponde, verificare con `docker compose ps` che PostgreSQL e Hermes siano avviati, che tutti i file dei segreti richiesti esistano e abbiano permessi `0600`, che il percorso del proxy corrisponda a `WHATSAPP_WEBHOOK_PATH` e che le credenziali esterne siano valide. Non stampare i segreti per diagnostica. I dettagli dei log non sono disponibili con l'attuale mitigazione della privacy.
