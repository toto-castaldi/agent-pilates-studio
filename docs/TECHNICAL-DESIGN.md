# Technical design — agent-pilates-studio

**Target version:** v0.2.0

Questo documento registra le scelte iniziali e le decisioni aperte. Il comportamento richiesto è in `docs/REQUIREMENTS.md`; le sezioni non ancora definite non implicano che le integrazioni siano state verificate.

## 1. Initial architectural decisions

| Decision | Choice | Rationale |
| -------- | ------ | --------- |
| Runtime locale e produzione | Docker Compose; server Linux già predisposto in produzione | Avvio e gestione coerenti nei due ambienti. |
| Codice del progetto | TypeScript 5.9.3, Node.js LTS 24.14.0 e npm 11.9.0 | Stack e versioni di riferimento dello scaffold definiti da TEC-002; dipendenze fissate nel lockfile. Hermes mantiene i propri prerequisiti. |
| Dati | PostgreSQL e migrazioni Prisma | Database relazionale e schema gestito tramite codice e migrazioni versionate. |
| Agente e modello | Hermes con OpenRouter; modello configurabile | Separare l'ambiente agentico dal provider; SPIKE-001 ha verificato `openai/gpt-6.1-terra` e la risposta tramite Hermes nella prova documentata. |
| Canale | API WhatsApp Business tramite app Meta esistente | Usare la configurazione Meta già disponibile; SPIKE-001 ha verificato il collegamento tramite il gateway nativo di Hermes nella prova documentata. |
| Rilascio | Versioni fissate, aggiornamento avviato esplicitamente | Riproducibilità e controllo operativo, senza deploy automatico. |
| CI | GitHub Actions | Verificare il quality gate senza eseguire automaticamente il deploy. |

## 2. Context and main flows

L'operatore configura e avvia l'ambiente locale o di produzione, applica le migrazioni con credenziali dedicate e gestisce aggiornamenti e recupero. L'interlocutore autorizzato invia messaggi tramite WhatsApp Business; il componente di integrazione verifica il webhook e l'autorizzazione, inoltra la richiesta a Hermes e restituisce la risposta. Hermes usa OpenRouter e può accedere a PostgreSQL con il solo ruolo agente.

SPIKE-001 ha realizzato lo stack locale e verificato questo flusso in una prova reale con l'app Meta e OpenRouter; TEC-005 ha documentato e verificato la continuità operativa nei limiti descritti, e TEC-006 ha configurato la CI.

## 3. Modules

**MOD-001 — Agente:** soluzione dell'assistente dello studio nel repository corrente: componenti applicativi, runtime e configurazione, dati e migrazioni, integrazioni, operatività e CI. Il modulo non implica un repository o un submodule Git separato. Le aree seguenti sono componenti dello stesso modulo, non moduli distinti.

- **Runtime e configurazione:** servizi Compose, versioni fissate e configurazione esterna; TEC-002 e SPIKE-001. TEC-009 aggiunge un orchestratore locale Node.js che prepara dipendenze e file privati, avvia database e bootstrap, applica migrazioni e attende la salute dei servizi.
- **Dati e migrazioni:** PostgreSQL, ruoli e migrazioni Prisma; SPIKE-001. L'agente esegue SQL direttamente tramite un piccolo plugin nativo Hermes, senza MCP; il ruolo PostgreSQL limita i privilegi.
- **Agente e modello:** installazione Hermes, configurazione OpenRouter e accesso ai dati con ruolo limitato; SPIKE-001.
- **Canale WhatsApp:** gateway WhatsApp Cloud nativo di Hermes con app Meta, validazione webhook e autorizzazione dei numeri; percorso del webhook configurabile per riutilizzare un callback HTTPS esistente; SPIKE-001.
- **Operatività e CI:** installazione, aggiornamento, recupero, osservabilità e verifiche automatiche; TEC-005 e TEC-006.

Hermes fornisce l'adattatore WhatsApp Cloud nativo; il progetto aggiunge un plugin SQL e un broker separato. TEC-010 collega il webhook autenticato al turno effettivo e al plugin tramite metadati interni, non argomenti del modello. Il broker verifica autonomamente la firma e l'allowlist e registra il contesto della transazione in PostgreSQL.

## 4. Data model

Il database applicativo è PostgreSQL 17.10, fissato per digest in Compose; lo schema è gestito con Prisma 7.10.1 e migrazioni versionate. L'accesso diretto di Hermes usa un plugin nel formato Python richiesto dal suo runtime e il driver `asyncpg` già presente nell'immagine; non introduce un servizio MCP. Lo schema `app` appartiene al ruolo di migrazione; i metadati Prisma risiedono in `public`, senza accesso da parte dell'agente.

TEC-010 introduce con una migrazione `app.clients` (nome e cognome univoci senza distinzione tra maiuscole e minuscole, data e autore di creazione), `app.training_rules` (testo, inserimento e disattivazione con rispettivi autori), `app.rule_slots` (giorno ISO e ora) e `app.rule_clients` (legame N:N). Il contesto autore è in `studio_private.author_context`, inaccessibile all'agente; `studio_private.consumed_messages` contiene impronte temporanee degli ID già utilizzati per impedire replay dopo un riavvio.

Hermes usa anche SQLite per le proprie sessioni; questo archivio è distinto da PostgreSQL e contiene dati sensibili. TEC-005 ha verificato persistenza e recupero complessivi, anche con dati reali e ripristino isolato.

## 5. Invariants and consistency

- L'agente può eseguire DML, non DDL; il vincolo va applicato e verificato sul database reale, non solo nelle istruzioni all'agente.
- Credenziali e privilegi delle migrazioni sono separati e non disponibili all'agente. I ruoli PostgreSQL sono distinti per amministrazione, migrazione e agente; solo quest'ultimo riceve DML nello schema applicativo. Il ruolo agente non possiede schemi né può creare tabelle temporanee; `pg_hba.conf` limita il suo accesso al database applicativo. PostgreSQL consente però al ruolo di login di cambiare la propria password anche senza `CREATEROLE`: l'utente ha accettato questa eccezione standard, che non consente DDL sugli schemi. Il bootstrap eseguito dall'operatore ripristina la password a partire dal file esterno. SPIKE-001 ha verificato il plugin tramite il registro dei tool Hermes contro PostgreSQL reale e con una chiamata generata dal modello durante una conversazione WhatsApp reale.
- Solo numeri configurati possono interagire; le richieste webhook non autentiche sono rifiutate.
- Per l'autore di clienti e regole, il broker usa il login `studio_broker`, senza DML sulle tabelle applicative né DDL, e registra un contesto protetto associato a PID e ID della transazione. I trigger con `SECURITY DEFINER` e `search_path` fisso controllano scadenza e associazione, sovrascrivono i valori forniti dall'agente e impediscono di modificare l'autore dei clienti. Un GUC modificabile dall'agente non è fonte di fiducia. Il plugin rifiuta i turni privi di prova attendibile; l'agente non accede alla tabella privata né assume il ruolo broker.
- L'agente non ha `DELETE` sulle regole e può aggiornare solo i campi di disattivazione; trigger rifiutano anche `DELETE` e `TRUNCATE` da parte del ruolo di migrazione e una seconda disattivazione. Un vincolo richiede data, numero e motivo coerenti; il nome del profilo è facoltativo.
- Aggiornamenti e riavvii preservano i dati; una procedura di ripristino deve essere verificata.

Il gateway inoltra al broker il corpo grezzo prima che l'adattatore lo verifichi a sua volta; il broker controlla HMAC, Phone Number ID, allowlist, mittente e timestamp firmato. Per un turno WhatsApp diretto usa l'ID del messaggio e il mittente forniti dal gateway, insieme a un nonce generato dal codice fidato; il nome proviene soltanto dal payload firmato. Il plugin avvia una transazione, ne invia PID e ID al broker tramite canale autenticato e poi esegue la query. Il contesto scade dopo 60 secondi ed è rimosso dopo commit/rollback o, in caso di interruzione, dalla pulizia periodica; l'impronta dell'ID già usato è conservata per 15 minuti. I messaggi sono accettati solo entro 5 minuti dal timestamp firmato, con 30 secondi di tolleranza futura: un messaggio tardivo o un turno interrotto dal riavvio del broker richiede un nuovo messaggio. Le ricevute in memoria hanno durata e numero limitati; in caso di esaurimento, errore del broker o prova assente il tool fallisce senza usare un'identità alternativa.

L'orologio dell'host deve essere affidabile e sincronizzato. Un ripristino di backup può riportare indietro anche lo storico delle impronte anti-replay: prima di riesporre il webhook attendere almeno 5 minuti e 30 secondi dall'ultimo webhook ricevuto prima del ripristino, senza accettare nuovi webhook nel frattempo.

Il broker non pubblica porte sull'host e riceve una credenziale database propria e un token condiviso solo col gateway; non riceve credenziali agente, amministrative o di migrazione. Il modello può invocare solo il tool SQL: la configurazione è restrittiva e i due percorsi di esecuzione dei tool applicano un'ulteriore allowlist. I componenti dell'host e i processi con accesso al token restano fidati. L'adattamento usa metodi interni della versione Hermes fissata e la restituzione del corpo a `aiohttp`: ogni aggiornamento dell'immagine richiede la ripetizione delle prove, non si presume compatibilità con altre versioni.

## 6. Integrations

- **Hermes:** immagine ufficiale v0.22.7 fissata per digest e avviata in Compose; verifica in SPIKE-001.
- **OpenRouter:** provider configurato esternamente; SPIKE-001 ha verificato l'ID `openai/gpt-6.1-terra` e una risposta reale tramite Hermes. Il modello resta configurabile.
- **WhatsApp Business:** gateway nativo con l'app Meta esistente; SPIKE-001 ha verificato webhook, allowlist e una conversazione reale. BUG-001 passa il canale home dal file privato a `WHATSAPP_CLOUD_HOME_CHANNEL`, supportata dal plugin Hermes 0.22.7; il gateway rifiuta valori mancanti o non presenti nell'allowlist. Il gestore interno `_handle_set_home_command` è sostituito con un rifiuto fisso, senza mutare configurazione o variabili persistenti.
- **PostgreSQL:** plugin SQL nativo e privilegi distinti verificati su PostgreSQL reale, anche tramite una chiamata generata dal modello in SPIKE-001.
- **Contesto dello studio:** TEC-011 monta `hermes/SOUL.md` in sola lettura su `/opt/data/SOUL.md`, unica fonte delle regole di comportamento. Prima di avviare il gateway il launcher richiede `sessions refresh-prompts` per tutte le sessioni del profilo e fallisce se la richiesta non riesce; la ricostruzione avviene al turno successivo, non durante un turno. La cronologia e i vecchi prompt restano nel volume SQLite. Memoria, profilo e provider esterni sono disabilitati. Il dispatcher aggiunge data e ora Europe/Rome alla sola copia del messaggio di sistema inviata al modello per ogni richiesta, senza salvarla nel prompt o nella cronologia; il fuso è configurato anche in Hermes e l'orologio host deve essere sincronizzato. Questo adattamento usa un punto interno dell'immagine fissata e richiede nuova verifica agli aggiornamenti. Il controllo anti-injection del loader non costituisce un blocco affidabile.

## 7. Security and observability

Segreti e credenziali restano fuori dal repository; gli esempi di configurazione non contengono valori reali. TEC-021 consente un link simbolico per `.env`: apre in modalità non bloccante, controlla tipo e bit di permesso sul descrittore e legge dallo stesso file, richiudendolo; i file segreti separati continuano a rifiutare link. Il controllo non verifica ACL e non protegge da operatori concorrenti o modifiche in loco del file. Con TEC-009 l'operatore mantiene `.env` e i file separati dei segreti privati: l'orchestratore rifiuta file o directory non privati, non sovrascrive segreti esistenti e arresta l'avvio se non corrispondono. Compose riceve solo le opzioni non segrete e i percorsi dei file; Hermes non riceve né `.env` né i segreti di amministrazione o migrazione. Tra le credenziali database, il processo Prisma riceve solo quella di migrazione necessaria. Gli output grezzi dei sottoprocessi sono soppressi e il comando emette solo eventi e messaggi di errore fissi. Non è prevista protezione contro operatori concorrenti; usare un solo operatore. I log non devono includere messaggi, numeri di telefono o credenziali. L'accesso al database è limitato con ruoli distinti; l'integrazione WhatsApp autentica le richieste e applica la lista dei numeri autorizzati. TEC-005 documenta e verifica stato, disponibilità e consultazione dei log; il monitoraggio avanzato è fuori scope.

Il launcher fidato di BUG-001 sostituisce anche la selezione del provider cron con un provider inattivo e disabilita il recupero dei job scaduti nella manutenzione del gateway; disabilitare il solo tool `cronjob` non ferma lo scheduler. Questi sono punti interni dell'immagine Hermes fissata e vanno riverificati a ogni aggiornamento. La regressione usa un job sintetico scaduto e webhook firmati, con sostituti locali Meta e modello; non verifica l'uso di servizi reali. L'accesso alla CLI dell'operatore resta separato e non autorizza job pianificati.

Per REQ-NFR-004, la procedura di TEC-005 deve vietare agli operatori l'avvio dello streaming remoto dei log del tunnel condiviso tramite dashboard Cloudflare, `cloudflared tail` o strumenti equivalenti. Il divieto è operativo e non impedisce tecnicamente l'avvio da parte di utenti autorizzati; non è prova della sicurezza di altri log Cloudflare o dei log locali, che restano soggetti a REQ-NFR-002.

L'adattatore WhatsApp nativo di Hermes può registrare numeri nei log e PostgreSQL può registrare query e valori. Gli entrypoint deviano stdout/stderr verso `/dev/null` prima di avviare i rispettivi processi; un descrittore separato, chiuso prima dell'avvio dei figli, invia al driver Docker `local` solo gli eventi fissi `hermes_launch`, `hermes_preflight_failed` e `postgres_launch`. Il launcher del gateway disabilita inoltre il logging Python prima di importare Hermes. La rotazione è limitata a tre file da 1 MB; gli eventi non attestano che i servizi siano sani. Stato e disponibilità richiedono Compose e healthcheck; dettagli degli errori non sono disponibili. I test esercitano messaggi, numeri, token sintetici e un errore SQL su PostgreSQL reale e controllano che i log contengano solo eventi fissi; ciò non prova l'assenza di ogni possibile fuga. Evitare modalità alternative di avvio non protette.

SPIKE-001 ha verificato isolamento dei segreti di migrazione, webhook e allowlist con test locali e una conversazione reale. Durante TEC-005, una richiesta sintetica al proxy HTTPS condiviso con origine non disponibile ha ricevuto 502 e il parametro di verifica sintetico è comparso nel journal di cloudflared. L'operatore ha installato un filtro systemd mirato all'hostname: due nuovi 502 sintetici non hanno prodotto i rispettivi valori nel journal, con controllo positivo su un evento precedente. Il filtro elimina l'intera riga e non copre tutti i formati né i log esterni. L'operatore dichiara che non sono configurate esportazioni Cloudflare e che non verranno configurate; tale scelta non esclude la conservazione di eventi in Cloudflare. Restano da verificare i dataset e i campi raccolti da Cloudflare e i formati locali. L'operatore ha autorizzato una prova pubblica temporanea e controllata accettando questo rischio residuo, con i limiti di REQ-NFR-002; non ha autorizzato l'uso continuativo. Lo streaming remoto del tunnel è vietato da REQ-NFR-004 e non viene avviato per la verifica. Il token reale attuale non è stato rilevato nella ricerca limitata nel journal locale: questa ricerca non dimostra che non sia presente altrove. TEC-005 ha verificato backup e diagnostica applicativa; l'audit completo del proxy è separato in TEC-008. Non assumere che una configurazione predefinita di Hermes soddisfi questi requisiti.

## 8. Test strategy

TEC-015 separa il gate rapido dalle prove con effetti reali. `npm test` ricompila ed esegue soltanto test unitari in memoria, con runner senza isolamento a processi; i test non avviano processi e non usano filesystem, Git, rete o Docker. La compilazione resta parte del comando e usa processi e filesystem. Le dipendenze sono preparate da lockfile con `npm ci`; `npm run build` continua a rigenerare `dist/`.

`npm run test:local` esercita Git reale, filesystem e processi sintetici, oltre al contratto del workflow effettivo; verifica anche l'allowlist Pi e la presenza e il contenuto dei template `/start` e `/work-alone` in un clone pulito del commit corrente, senza leggere impostazioni personali. `test:pi` verifica in isolamento che Pi rilevi entrambi i template con fiducia accordata e non li rilevi senza fiducia, senza invocare un modello; non verifica l'osservanza delle istruzioni né il ricaricamento interattivo. La logica di avvio e inizializzazione dei segreti è separata dagli effetti e verificata anche in memoria. Le prove locali e le suite `test:pi`, `test:pi-package`, `test:db`, `test:hermes`, `test:author`, `test:upgrade` e `test:start` si eseguono durante gli item quando necessarie, tutte alla chiusura della versione e in CI. Le prove reali Meta/OpenRouter, con servizi e credenziali esterni, sono documentate e valutate separatamente. Nessun test simulato sostituisce PostgreSQL reale per privilegi e migrazioni.

Per gli host Linux con Docker ma senza Node.js, TEC-005 introduce un'immagine temporanea di migrazione costruita da Node.js 24.14.0 fissato per digest e dal lockfile. L'installazione delle dipendenze precede il montaggio del solo segreto di migrazione; l'immagine usa la rete host per raggiungere PostgreSQL su loopback e non viene montata in Hermes. Il contesto Docker esclude configurazione locale e segreti. La prova PostgreSQL verifica anche questo percorso.

Per la continuità, l'operatore arresta Hermes, il broker e gli altri scrittori prima di catturare dump PostgreSQL e volume Hermes completo. I contesti effimeri delle transazioni sono esclusi dal dump, mentre le impronte anti-replay sono conservate. Gli script creano un backup privato in una directory nuova con somme di controllo e ripristinano solo in un nuovo progetto Compose con porta loopback effimera, senza avviare Hermes. È richiesta una destinazione cifrata esterna e una copia separata dei segreti: gli script non garantiscono cifratura, autenticità del backup o mutua esclusione contro altri operatori. Il test di integrazione ripristina PostgreSQL e lo stato SQLite reale di Hermes su risorse isolate, verifica privilegi e casi di rifiuto, e prova la persistenza dopo riavvio e ricreazione con la stessa immagine. Un test separato verifica, con dati sintetici e servizi in rete isolata, l'aggiornamento reale PostgreSQL 17.9→17.10 e Hermes 0.22.6→0.22.7, inclusa la persistenza e il divieto di DDL; è stato eseguito anche su `jarvis`. Su `jarvis` gli script sono stati verificati con PostgreSQL reale e, in rete isolata, con lo stato SQLite sintetico creato da Hermes reale. Dopo la prova pubblica temporanea è stato inoltre creato su disco LUKS e ripristinato in isolamento un backup dello stato reale, senza esporre il contenuto; una copia indipendente è stata verificata su disco esterno LUKS. Su autorizzazione è stata verificata anche una copia dei segreti in directory distinta sullo stesso disco; la passphrase deve essere conservata separatamente. Il PostgreSQL operativo è stato riavviato e riconfigurato sulla stessa immagine e volume; migrazioni, autenticazione agente, rifiuto del DDL e persistenza dei dati controllati sono stati verificati. Le verifiche non garantiscono la compatibilità di altre versioni.

Il progetto usa Biome 2.6.5 per il lint del codice TypeScript e degli script, TypeScript per controllo dei tipi e build e il test runner integrato di Node.js per i test; `npm test` ricompila prima di eseguirli. `npm run test:db` esegue le prove di migrazione e privilegi su PostgreSQL reale e verifica il plugin SQL tramite il registro Hermes. `npm run test:hermes` avvia lo stack in una rete Docker isolata e verifica gateway nativo, autenticazione e autorizzazione con dati sintetici e protezioni dei log. `npm run test:author` usa gateway reale, modello deterministico locale e PostgreSQL reale: verifica due mittenti concorrenti, insert e disattivazione, autori falsificati dal modello, accessi negati, firme, allowlist, messaggi scaduti, concorrenza e replay dopo riavvio del broker. `npm run test:start` usa un progetto Compose temporaneo, configurazione sintetica e una rete interna per Hermes: verifica avvio da copia senza dipendenze o volumi, migrazioni, DML e rifiuto DDL, isolamento dei segreti, riavvio e persistenza PostgreSQL e Hermes, e nuovo avvio dopo rimozione dei soli volumi di test. I test unitari verificano configurazione, errori e soppressione dell'output; quelli di integrazione usano PostgreSQL reale per migrazioni e privilegi. I test dei webhook includono autenticazione e accessi negati. Le prove end-to-end reali con Meta e OpenRouter richiedono configurazione, rete e credenziali esterne e sono documentate separatamente; non sostituiscono i test automatici. TEC-005 verifica anche aggiornamento, persistenza e ripristino.

TEC-024 aggiorna il visualizzatore Pi alla v1.5.0 mantenendo il supporto dello studio per item non assegnati su una riga e metadati epic nel corpo. L'estensione legge `BACKLOG.md` a ogni apertura, filtra per tipo, priorità e stato e integra gli stati dai branch locali e remote-tracking non integrati, segnalando provenienza e branch concorrenti. Un fetch in background aggiorna o elimina riferimenti remote-tracking ma non modifica i file del working tree; errori e limiti sono descritti nel README. Le impostazioni Pi per la scorciatoia sono lette alla registrazione. `test:pi` usa Pi 1.5.0 offline, directory e repository sintetici e uno pseudoterminale per verificare comando, filtri, branch, fetch, navigazione, scorrimento, errori, ricaricamento e scorciatoie; la prova non copre tutti i terminali o le dimensioni, né una sessione con modello. Git e `test:local` verificano l'allowlist selettiva e il flusso dei claim con remoti sintetici. La CI esegue le prove tramite i comandi già obbligatori.

TEC-014 verifica con `test:local`, senza leggere il contenuto delle impostazioni personali, i file Pi versionati, la protezione Git dei dati locali e la coerenza delle istruzioni di avvio. `npm run test:pi`, eseguito separatamente con Pi installato, avvia Pi direttamente offline con configurazioni ed estensioni sintetiche: controlla caricamento delle risorse, precedenza dei tool e comportamento delle scritture con directory personale e di progetto distinte o coincidenti. La prova non accede alle risorse personali dell'operatore né verifica la portabilità dei suoi pacchetti.

TEC-018 fissa il pacchetto pubblico `agent-harness-stuff` al commit `44f36742d47a4e83504abb9bdc0427be5f09ed82` e rimuove il pacchetto `npm:pi-question-tool` per evitare provider duplicati. Il fork mantiene contratto e licenza MIT dell'originale 0.1.1 e passa a `ctx.ui.custom()` l'opzione `blocked` di tipo `question`, con messaggi fissi che non contengono la domanda. `test:pi-package` installa il riferimento in un progetto temporaneo con rete e configurazione sintetica, controlla commit e provenienza, esegue i test del pacchetto e una prova Pi 1.5.0 offline in pseudoterminale. La prova OSC verifica `blocked` e il ritorno a `idle` per risposta e annullamento, non un turno reale del modello o la visualizzazione di tutti i terminali. Il confronto e la simulazione in memoria nel pacchetto verificano contratto e ripristino dello stato `working` simulato; non sostituiscono la prova di un turno reale. Il riferimento deve restare raggiungibile sul repository pubblico.

TEC-006 configura GitHub Actions su push, pull request e avvio manuale: un job Linux esegue il gate rapido e i test di integrazione PostgreSQL, Hermes, autore e aggiornamento, preparando prima le immagini Docker fissate dal progetto. TEC-009 aggiunge al job la prova isolata del comando unico; TEC-015 aggiunge `test:local` e `test:pi` offline con Pi 1.5.0; TEC-018 aggiunge `test:pi-package`, che richiede rete per l'installazione isolata del commit pubblico e dei test. Il job usa soltanto dati sintetici, permessi di lettura del repository e action fissate per commit; non esegue deploy e non richiede segreti GitHub. Un test del contratto interpreta il workflow con `yaml` 2.9.1 e verifica trigger, comandi, permessi e assenza di condizioni che permettano di saltare o ignorare i controlli.

TEC-012 aggiunge `npm run test:conversation`, separato dal gate e dalla CI: un catalogo JSON con stato iniziale, turni e aspettative guida uno stack Compose nuovo per scenario, con database e volume Hermes isolati, credenziali sintetiche e webhook firmato. Il gateway e il broker di produzione ricevono l'identità lungo il percorso autentico; un launcher solo di prova reindirizza le richieste HTTPX per `graph.facebook.com` a un sostituto locale Meta, mentre OpenRouter è reale. Il progetto Docker ha accesso esterno e non costituisce una sandbox di rete. US-002 estende il catalogo a più clienti e slot, gruppi, chiarimenti e tentativi di dichiarare l'autore. Il confronto controlla data, autore e associazioni cliente/slot, accettando scomposizioni diverse purché senza associazioni mancanti o duplicate; verifica anche indicatori lessicali del testo delle regole e delle risposte, comprese domande e orari, ma non certifica la semantica completa. Lo stato iniziale rimane vuoto e gli scenari creano i dati nei turni precedenti. Avvisi di canale home noti e progresso dei tool non sono trattati come risposta finale. Un relay autenticato da token sintetico inoltra le chiamate tramite un socket Unix privato a un proxy nel processo host, che aggiunge la chiave OpenRouter solo in memoria per il server HTTPS fisso; la chiave reale non è copiata nei file o nei container. Output grezzo e messaggi non sono registrati intenzionalmente. Pulizia e limiti sono descritti nel README, le evidenze in `docs/operations/TEC-012-prove.md`.

## 9. Configuration and local runtime

L'ambiente locale usa Docker Compose; TEC-009 usa Node.js e npm sull'host, `.env` privato e `npm run start:local`, senza esporre automaticamente il webhook pubblico. Il comando verifica i valori richiesti e i permessi, non elimina volumi e segnala fallimenti senza dichiarare sano lo stack; la salute locale non prova la disponibilità dei servizi esterni. Da TEC-011 avvia il broker separatamente e ricrea il solo gateway a ogni esecuzione: un checkout può sostituire l'inode del file montato e la ricreazione applica il contesto aggiornato, interrompendo eventuali turni in corso. La produzione presume un server Linux con Docker/Compose e un endpoint HTTPS pubblico già disponibili. DNS, certificati e provisioning del server sono fuori scope. Le variabili, gli esempi e i comandi operativi sono descritti nel README e nella procedura TEC-005; non inserire segreti reali. Node.js 24.14.0 è indicato in `.nvmrc`; gli intervalli supportati di Node.js e npm sono in `package.json`. Le immagini dei componenti sono fissate per digest nella configurazione.
