# Configuration and local runtime

## Pi workflow configuration

**Decisione del 2026-11-13 — REQ-NFR-022, attuata con TEC-045:** `.pi/workflow.json` è la fonte versionata delle sole chiavi `packages`, `skills`, `extensions` e `prompts`. Riferimenti fissati e selezione delle risorse condivise attuali vengono preservati; nessun aggiornamento implicito dei pacchetti. `.pi/settings.json` è un file locale persistente, ignorato, unico settings effettivo del progetto; `themes` e `theme`, come ogni chiave non gestita, restano locali. Non si introduce una seconda configurazione da far fondere a Pi né si impone una directory agente diversa da `.pi`.

`node scripts/start-pi.mjs` esegue dalla radice la sincronizzazione prima di avviare Pi e inoltra argomenti, stdio, segnali ed esito del processo; usa il modulo puro `src/pi-workflow.ts`, senza build preventiva. Il generatore valida il manifest rispetto all'insieme esplicito di chiavi gestite e legge l'eventuale settings come oggetto JSON; sovrappone soltanto tali chiavi, rimuovendo quelle gestite assenti dal manifest senza residui. Conserva ogni altra proprietà, compresi valori sconosciuti e oggetti annidati locali. La sincronizzazione è idempotente e non riscrive il file se invariato; una sostituzione atomica dopo la validazione evita file parziali. Errori fermano l'avvio con diagnostica senza contenuti del settings. Non viene ripristinato `scripts/pi.sh`: il launcher rifiuta `.pi` simbolica/non directory/scrivibile da altri e settings non regolari, simbolici o con hard link; usa temporanei esclusivi `0600`. Gruppo Unix fidato; nessuna protezione contro scrittori concorrenti, ACL o host compromessi: un solo operatore durante la preparazione. Procedura di recupero privato prima dell'aggiornamento, contratto e limiti sono in [TEC-045](operations/TEC-045-pi-workflow.md).

TEC-045 aggiorna allowlist Git, lettori del riferimento al pacchetto, documentazione, test e comando dei futuri worker in `AGENTS.md` §10, mantenendo `--approve`, inoltro degli argomenti e protezioni dei clone senza cambiare i documenti generici del processo. Avviare direttamente `pi` resta possibile ma non prepara la configurazione: è un limite esplicito, non una garanzia fornita da un'estensione caricata troppo tardi. La preparazione non accorda fiducia e non copia autenticazione, sessioni o stato personale. La migrazione documentata conserva il settings locale esistente fuori da Git e offre un recupero privato prima delle operazioni di transizione; un clone nuovo genera il file dal solo manifest. Non sono modificati impostazioni, avvii o worker durante la sola pianificazione; lo storico TEC-007/TEC-013/TEC-014 rimane tale.

Le funzioni pure di validazione e sincronizzazione sono coperte in memoria; `test:local` prova con repository e processi sintetici clone nuovo, transizione, idempotenza, aggiunte/rimozioni, preservazione dei valori locali, errori senza perdita, argomenti/esiti del launcher e assenza di diff Git dopo cambi di preferenze. `test:pi` verifica con Pi reale offline caricamento delle risorse sintetiche e persistenza delle preferenze, inclusi modello/thinking, con `PI_CODING_AGENT_DIR=./.pi`. Le suite pertinenti, inclusa `test:pi-package`, leggono il manifest condiviso anziché impostazioni personali; nessuna prova deve usare le credenziali dell'operatore. Le verifiche con filesystem, Git o processi restano fuori da `npm test` (§8).

## Studio runtime

L'ambiente locale usa Docker Compose; TEC-009 usa Node.js e npm sull'host, `.env` privato e `npm run start:local`, senza esporre automaticamente il webhook pubblico. Il comando verifica i valori richiesti e i permessi, non elimina volumi e segnala fallimenti senza dichiarare sano lo stack; la salute locale non prova la disponibilità dei servizi esterni. Da TEC-026 arresta il gateway con SIGKILL, per evitare avvisi di spegnimento al vecchio canale home, poi arresta il broker, aggiorna i file esterni e ricrea entrambi, applicando anche i file montati sostituiti da checkout. I turni in corso sono interrotti. Dopo un errore nell'aggiornamento tenta di arrestare entrambi; un guasto Docker può impedire l'arresto e richiede verifica manuale prima del recupero. I file parzialmente aggiornati vengono riallineati rilanciando il comando. La produzione presume un server Linux con Docker/Compose e un endpoint HTTPS pubblico già disponibili. DNS, certificati e provisioning del server sono fuori scope. Le variabili, gli esempi e i comandi operativi sono descritti nel README e nella procedura TEC-005; non inserire segreti reali. Node.js 24.14.0 è indicato in `.nvmrc`; gli intervalli supportati di Node.js e npm sono in `package.json`. Le immagini dei componenti sono fissate per digest nella configurazione.

Nella baseline il collegamento opzionale `WHATSAPP_TEACHER_LINKS` in `.env` è un array JSON di numero autorizzato, nome e cognome; l'assenza equivale a `[]`. I valori non validi arrestano `start:local` prima di modificare servizi o segreti, senza riportare numeri o nomi. Il file privato `whatsapp-teacher-links` è montato solo nel broker. In produzione `ops init`, installazione e aggiornamento predispongono il file vuoto se manca, senza sovrascriverlo; questa procedura resta quella eseguibile fino all'attivazione del nuovo modello.

Nel modello target l'unico numero personale configurato è `PILATES_MANAGER_PHONE`, in formato internazionale validato e normalizzato; il canale home ne deriva automaticamente. `WHATSAPP_ALLOWED_USERS`, `WHATSAPP_TEACHER_LINKS` e il numero home separato non sono più fonti applicative né fallback. Gli esempi e le procedure saranno aggiornati insieme al runtime, non durante questa pianificazione. Nome, cognome, telefoni degli altri insegnanti e accessi si mantengono soltanto nel database tramite il gestore. Censire un destinatario non supera il limite o la preregistrazione del numero di test Meta.

Il passaggio è coordinato: TEC-041 fornisce base dati additiva e funzioni protette, US-017 il percorso guidato verificato con webhook firmati, quindi TEC-042 sostituisce insieme i consumatori dell'identità e applica le restrizioni definitive su censimenti e lettura dei numeri, compresi gli autori storici. Non si attiva un gateway con una fonte e un broker con un'altra e non si mantiene una sincronizzazione permanente con i vecchi file. TEC-043 prova e documenta transizione e recupero del gestore preservando ID, snapshot e dati, senza avviare la produzione durante le prove. Distingue trasferimento della funzione gestionale a un'altra persona e cambio del numero della stessa persona: nel primo caso il vecchio numero perde i soli privilegi gestionali, nel secondo l'identità interna resta la stessa e il numero sostituito perde l'accesso. Il flusso ordinario in chat non può eseguire nessuna delle due operazioni.

Ambienti (REQ-OPS-004): i due ambienti usano lo stesso `compose.yaml`. Lo sviluppo mantiene il progetto Compose predefinito del repository; la produzione usa il progetto esplicito `agent-pilates-prod`, con configurazione e segreti fuori dal checkout e porte loopback distinte. `PILATES_VOLUME_PREFIX` determina insieme i nomi dei volumi PostgreSQL e Hermes; se non è impostato vale il nome del progetto, conservando i volumi esistenti. `start:local` verifica la configurazione risolta da Compose e rifiuta progetto e volumi di produzione; `restore.sh` ignora il prefisso ereditato per non puntare ai volumi di un altro ambiente.

Aggiornamento di produzione (REQ-OPS-005, REQ-OPS-007): procedura manuale su `jarvis`, eseguita dall'immagine `ops` che contiene `compose.yaml` e le procedure (`docs/operations/TEC-035-produzione.md`), estende `docs/operations/TEC-005-continuita.md` ed è distinta da `start:local`. Non è presente un checkout applicativo sul server; il solo launcher shell minimale di REQ-OPS-009 inoltra il comando all'immagine. `compose.yaml` non monta file del checkout; le immagini sono parametriche per ambiente (`PILATES_HERMES_IMAGE`, `PILATES_POSTGRES_IMAGE`) e lo sviluppo le costruisce in locale. `SOUL.md`, configurazione e plugin sono montati in sola lettura dall'immagine stessa con mount `type: image`, dentro `/opt/data`: una copia nel volume permetterebbe all'agente, che ne possiede la directory, di sostituirli, e un volume esistente non riceverebbe i file nuovi. Richiede un Docker che accetti più mount `subpath` dalla stessa immagine: la 28.0.4 li rifiuta, la 29.9.2 di `jarvis` li accetta e la CI installa la stessa versione. Le migrazioni vanno solo avanti: il ritorno alla versione precedente riparte da un backup ripristinato in volumi nuovi, selezionati con `PILATES_VOLUME_PREFIX`, conservando quelli precedenti.

Launcher manuale (REQ-OPS-009): `scripts/update-agent-pilates.sh`, copiabile come `~/update-agent-pilates.sh`, richiede un solo SHA completo minuscolo e non contiene un commit predefinito. Dopo la validazione esegue `docker run --rm` dell'immagine `ops` di quel commit con gli unici bind mount del socket Docker e di `/opt/agent-pilates-prod`, poi `update` con lo stesso SHA; nessun checkout, build o ricerca automatica di versioni sul server. Propaga l'esito di Docker senza dichiarare un successo proprio. La selezione della versione è un comando separato dell'operatore: GitHub CLI può leggere il tip di `main`, oppure l'ultimo run riuscito di `ci.yml` filtrato per `main` ed evento `push`, che comprende la pubblicazione. La procedura documenta installazione del launcher, distinzione dei due riferimenti e aggiornamento manuale. I test locali usano un Docker sostitutivo su `PATH` con soli dati sintetici per controllare argomenti, rifiuti ed errori; l'installazione su `jarvis` verifica solo copia, sintassi e aiuto e non avvia l'aggiornamento.

Backup a caldo (REQ-OPS-008): `ops backup-hot <commit>` richiede il commit completo dell'immagine `ops`, che può essere più recente di quella in esercizio. Esegue `pg_dump -Fc` nel PostgreSQL sano del progetto attivo, con la stessa esclusione del backup quiescente, senza fermare o ricreare gateway e broker e senza copiare il volume Hermes. Una directory nuova `hot-*` sotto `backups/` è privata; `INCOMPLETE` viene rinominato atomicamente in `COMPLETE` con valore `hot-postgres-v1` solo dopo dump, checksum e proprietà. L'assenza del marcatore completo indica un errore anche se la creazione di `INCOMPLETE` è stata interrotta. Il rollback che include TEC-039 verifica prima degli arresti formato quiescente, marcatore `1`, entrambi gli archivi e i checksum; `restore.sh` ripete la verifica. Le immagini `ops` precedenti possono fermare i servizi prima di rifiutare il backup. Un solo operatore alla volta; checksum e permessi non garantiscono autenticità, cifratura, assenza di ACL o mutua esclusione. Il ripristino locale senza proprietari e privilegi è solo per consultazione, non sostituisce quello quiescente. Nessun automatismo avvia il backup in produzione; la CI lo esercita soltanto nel progetto sintetico isolato.

WhatsApp per ambiente (REQ-OPS-006): si usano due app Meta anziché una con override del callback per numero, per non condividere l'app secret con i clone di sviluppo. Il tunnel esistente instrada l'hostname di produzione verso la porta loopback di produzione su `jarvis` e quello di sviluppo verso la porta a cui si collega il clone con `ssh -R`. Il filtro `LogFilterPatterns` di cloudflared copre entrambi gli hostname, come verificato da TEC-008 con `proxy:audit`. La produzione parte con il numero di test Meta della propria app (decisione del 2026-11-10 in REQ-OPS-006): i destinatari sono anche registrati nell'elenco del numero di test su Meta. Nella baseline il passaggio a un numero reale aggiorna i segreti `whatsapp-*` di produzione e l'allowlist; nel modello target non esiste l'allowlist applicativa e il censimento nel database rimane indipendente dalla configurazione del trasporto. Il cambio dei segreti richiede il riavvio coordinato con la procedura di TEC-035. Numero di test, account WhatsApp ed elenco destinatari appartengono al Business portfolio, non all'app: la produzione ha quindi un portfolio Meta proprio, con app pubblicata, solo il campo `messages` e l'app iscritta all'account WhatsApp. Il pannello indica al massimo 5 destinatari; la durata del numero di test non è documentata nelle fonti consultate. Il percorso pubblico di produzione è limitato a `/whatsapp/webhook`; il resto dell'hostname risponde 404. Procedura ed evidenze in `docs/operations/TEC-036-whatsapp-ambienti.md` (TEC-036).
